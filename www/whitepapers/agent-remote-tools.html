Internal vs Remote Tools — How AI Agent Frameworks Wire In Each

A reference map of where tools can live across ten AI agent frameworks — spanning Python, TypeScript, .NET, Java, Go, and Rust — and the official declaration and call mechanism for each: in-process code, MCP servers, OpenAPI specs, remote agents over A2A, and generic RPC. Every code snippet is taken from the framework's own documentation.

The five wiring points LangChain LangGraph CrewAI Google ADK Semantic Kernel Mastra MS Agent Framework LangChain4j Genkit Go Rig Side-by-side Cheat sheet

The five places a tool can live

Across the ten frameworks profiled here, tools are sourced from five categories. The framework determines which categories have first-class APIs and which require custom code. Each category is described below; per-framework support is summarised in the side-by-side table.

INTERNAL In-process code

A function, class, or annotated method that runs in the agent's own runtime. Schema is derived from the host language's type system or from explicit metadata.

MCP Model Context Protocol

An open JSON-RPC protocol for tool servers, defined at modelcontextprotocol.io. The current transports are stdio (subprocess) and Streamable HTTP; legacy SSE remains supported by some framework integrations for compatibility. Tools are discovered at runtime via tools/list.

OPENAPI REST / OpenAPI

The framework parses an OpenAPI 3.x specification and generates one tool per operation, with parameters typed from the spec.

A2A Remote agent (A2A)

Another agent running on a different host, described by an agent-card.json at a .well-known/ URL, invoked over HTTP per the A2A protocol.

RPC Generic RPC / gRPC

No framework on this list provides a first-class generator from a gRPC / Thrift / other RPC schema. The documented pattern is to call the RPC client from within an in-process tool body.

Ten frameworks, five wiring points

Each card lists the in-process baseline (recapped from the companion paper How AI Agent Frameworks Wire In Tools and Agents), then the framework's documented mechanism for MCP, OpenAPI, A2A, and generic RPC. Highlighted spans mark the line of code where each external tool source is attached to the agent.

Lc

LangChain Python

Decorator for internal; langchain-mcp-adapters for MCP; community RequestsToolkit for OpenAPI.
All external tool sources are exposed through adapter packages that produce a list of LangChain tools, which is passed to create_agent.
Internal

Recap: the @tool decorator turns a function into a tool; pass the list to create_agent.

from langchain.tools import tool
from langchain.agents import create_agent

@tool
def search_database(query: str) -> str:
    """Search the customer database."""
    return f"results for {query}"

agent = create_agent("openai:gpt-4o", tools=[search_database])
Source: docs.langchain.com · Tools · @tool decorator + create_agent
MCP

The langchain-mcp-adapters package ships MultiServerMCPClient, which connects to one or many MCP servers (stdio, SSE, or streamable HTTP) and returns a list of LangChain tools.

from langchain_mcp_adapters.client import MultiServerMCPClient
from langchain.agents import create_agent

client = MultiServerMCPClient({
    "math": {
        "transport": "stdio",
        "command": "python",
        "args": ["/path/to/math_server.py"],
    },
    "weather": {
        "transport": "streamable_http",
        "url": "http://localhost:8000/mcp",
    },
})

tools = await client.get_tools()
agent = create_agent("anthropic:claude-sonnet-4-6", tools=tools)
Source: docs.langchain.com · MCP · MultiServerMCPClient
OpenAPI / REST

Use RequestsToolkit from langchain_community to expose generic HTTP verbs, then pair with prompt-based OpenAPI guidance. There is no auto-generator from spec to typed tools in core; the langchain-community openapi planner is the closest first-class option.

    allow_dangerous_requests=True,

Remote agent (A2A)

Not first-class in LangChain core. The recommended path is LangGraph's RemoteGraph (see next card) — wrap a deployed graph and embed it as a tool or subgraph.

Generic RPC

Open the gRPC / Thrift / custom-RPC client inside the body of an @tool-decorated function. LangChain doesn't add anything special; the tool is just a callable.

Mechanism

All external tool sources are converted to LangChain BaseTool instances by adapter packages.

Notes

OpenAPI / REST

Same as LangChain — use RequestsToolkit or community OpenAPI planners. There is no LangGraph-specific OpenAPI loader.

Remote agent (A2A) — RemoteGraph

RemoteGraph connects to a deployed LangGraph Platform graph at the given url and exposes the same interface as a local compiled graph. It can be invoked directly or embedded as a node in a parent graph.

from langgraph.pregel.remote import RemoteGraph
from langgraph.graph import StateGraph, MessagesState

# Connect to a graph deployed on LangGraph Platform
remote_graph = RemoteGraph("research_agent", url="https://<deployment>.langgraph.cloud")

# 1. Call it directly
result = await remote_graph.ainvoke(
    {"messages": [{"role": "user", "content": "analyse Q1 earnings"}]}
)

# 2. Or embed it as a subgraph node in a larger orchestrator
builder = StateGraph(MessagesState)
builder.add_node("researcher", remote_graph)   # remote graph as a local node
builder.add_edge("researcher", "writer")
super_graph = builder.compile()
Source: docs.langchain.com · LangSmith · Use RemoteGraph
Generic RPC

Wrap the RPC client in any LangChain tool, or inside a custom node function — graph nodes are async Python callables.

Mechanism

RemoteGraph uses the LangGraph SDK over HTTP. Checkpointer state is maintained on the remote deployment.

Constraints

The remote endpoint must implement the LangGraph Platform API; arbitrary HTTP agents are not directly supported.

MCP — the mcps= field

The mcps= list on Agent accepts string references (remote HTTPS URLs or catalog slugs) and structured transport objects (MCPServerStdio, MCPServerHTTP, MCPServerSSE) in the same list. Stdio, streamable HTTP, and SSE transports are supported.

from crewai import Agent
from crewai.mcp import MCPServerStdio, MCPServerHTTP, MCPServerSSE

agent = Agent(
    role="Research Analyst",
    goal="Research with full control over MCP connections",
    backstory="Expert researcher",
    mcps=[
        # String reference — remote HTTPS MCP server
        "https://mcp.exa.ai/mcp?api_key=your_key",
        # Stdio transport for a local subprocess MCP server
        MCPServerStdio(
            command="npx",
            args=["-y", "@modelcontextprotocol/server-filesystem"],
        ),
        # Streamable HTTP for a remote MCP server
        MCPServerHTTP(
            url="https://api.example.com/mcp",
            headers={"Authorization": "Bearer your_token"},
        ),
    ],
)
Source: docs.crewai.com · MCP overview · Structured Configurations (mcps= field)
OpenAPI / REST

    name="github_agent",

    tools=[mcp_toolset],
)

Sk

Microsoft Semantic Kernel Python

Plugins are the universal abstraction: MCPStdioPlugin, add_plugin_from_openapi, all registered on the Kernel.
All tool sources are represented as plugins registered on the Kernel. With FunctionChoiceBehavior.Auto(), the Kernel resolves and invokes the matching plugin function.
Internal

Recap: a class of @kernel_function-decorated methods, registered on the Kernel.

from semantic_kernel import Kernel
from semantic_kernel.functions import kernel_function

class WeatherPlugin:
    @kernel_function(description="Gets the weather for a city")
    def get_weather(self, city: str) -> str: return f"sunny in {city}"

kernel = Kernel()
kernel.add_plugin(WeatherPlugin(), plugin_name="weather")

An MCP server is wrapped as a plugin via an async context manager (MCPStdioPlugin for stdio transport, MCPSsePlugin for SSE) and registered on the Kernel via kernel.add_plugin.

         os.getenv("GITHUB_PERSONAL_ACCESS_TOKEN")},
) as github_plugin:
    kernel = Kernel()
    kernel.add_plugin(github_plugin)

Remote agent (A2A)

No first-class A2A primitive in the Python SDK. The documented pattern is to expose the producing agent's Kernel as an MCP server (via kernel.as_mcp_server) and consume it from the calling agent via MCPStdioPlugin or MCPSsePlugin.

MCP — transport → client → provider

Construct an McpTransport (stdio, streamable HTTP, WebSocket, or Docker), wrap it in a DefaultMcpClient, register the client with an McpToolProvider, and attach the provider to the AI service via AiServices.builder(...).toolProvider(...).

// 1. Transport — start an MCP server as a subprocess
McpTransport transport = StdioMcpTransport.builder()
    .command(List.of("/usr/bin/npm", "exec",
        "@modelcontextprotocol/server-everything@0.6.2"))
    .build();

// 2. Client
McpClient mcpClient = DefaultMcpClient.builder()
    .key("MyMCPClient")
    .transport(transport)
    .build();

// 3. Tool provider — optionally filter which tools to expose
McpToolProvider toolProvider = McpToolProvider.builder()
    .mcpClients(mcpClient)
    .filterToolNames("get_issue", "list_issues")
    .build();

// 4. Wire into AI service
Bot bot = AiServices.builder(Bot.class)
    .chatModel(model)
    .toolProvider(toolProvider)
    .build();

MCP — MCPManager

The plugins/mcp package provides NewMCPManager, which holds multiple MCP server connections. Servers may be declared up front via MCPManagerOptions.MCPServers or added at runtime via ConnectServer.

package main

import (
    "context"
    "log"

    "github.com/firebase/genkit/go/genkit"
    "github.com/firebase/genkit/go/plugins/mcp"
)

func main() {
    ctx := context.Background()
    g, _ := genkit.Init(ctx)

    // Configure one or more MCP servers up front
    manager, err := mcp.NewMCPManager(mcp.MCPManagerOptions{
        Name: "my-app",
        MCPServers: map[string]mcp.MCPClientOptions{
            "everything": {
                Name: "everything-server",
                Stdio: &mcp.StdioConfig{
                    Command: "npx",
                    Args:    []string{"-y", "@modelcontextprotocol/server-everything"},
                },
            },
        },
    })
    if err != nil { log.Fatal(err) }

    // Connect additional servers at runtime
    _ = manager.ConnectServer(ctx, "weather", mcp.MCPClientOptions{
        Name: "weather-server",
        Stdio: &mcp.StdioConfig{Command: "python", Args: []string{"weather_server.py"}},
    })
}
Source: pkg.go.dev · firebase/genkit/go/plugins/mcp · NewMCPManager + ConnectServer

MCP — rmcp integration

The rmcp Cargo feature enables the official Rust MCP SDK. The application connects to an MCP server through rmcp transports, lists tools, and attaches each to a Rig agent (or to a shared ToolServer handle) via .rmcp_tool(tool, peer) on the agent builder. The earlier mcp-core integration is deprecated and scheduled for removal in 0.18.

)?;
let mcp_client = ().serve(transport).await?;

// 2. Discover its tools and attach them to a Rig agent
let tools = mcp_client.list_tools(Default::default()).await?;
let mut builder = openai::Client::from_env()
    .agent("gpt-4o")
    .preamble("Use the available MCP tools.");

for tool in tools.tools {
    builder = builder.rmcp_tool(tool, mcp_client.peer().clone());
}
let agent = builder.build();

OpenAPI

No first-class OpenAPI loader. The documented pattern is to generate a typed client from the spec (e.g. with progenitor or openapitor) and call it from a Rig Tool implementation.

Remote agent (A2A)

No first-class A2A primitive. Tool sharing across agents in the same process is supported by the ToolServer handle. For cross-process coordination, the documented pattern is to expose the agent as an MCP server via rmcp and consume it via the MCP pattern above.

Generic RPC

No first-class gRPC binding. The documented pattern is to call Tonic (or another Rust RPC client) inside a Tool trait implementation.

Mechanism

MCP integration uses the official Rust MCP SDK (rmcp) under the rmcp Cargo feature.

Notes

The mcp-core → rmcp migration is in progress; the mcp-core integration is scheduled for removal in 0.18.

Summary observations

Six factual observations drawn from the per-framework data above.

MCP

1 · MCP consumer support is present in all ten frameworks

Every framework profiled here ships first-class MCP consumer support, either in core or via an officially-maintained adapter package. MCP server (producer) support is present in six: ADK, Semantic Kernel, Mastra, Genkit Go, Rig, and via separate packages in the LangChain/LangGraph and CrewAI ecosystems.

DECLARATION

2 · Declaration patterns fall into three shapes

A single constructor field listing all sources (CrewAI mcps=, Mastra tools: / agents:); a dedicated class per source (ADK MCPToolset / OpenAPIToolset / RemoteA2aAgent); or a builder pipeline (LangChain4j transport → client → provider → AI service).

A2A

3 · Four frameworks expose a first-class A2A primitive

ADK (RemoteA2aAgent), CrewAI (A2AClientConfig), Mastra (A2AAgent), and LangGraph (RemoteGraph, requires a LangGraph Platform endpoint). In the other six frameworks, remote-agent access is documented via MCP composition.

OPENAPI

4 · First-class OpenAPI ingestion is present in three frameworks

ADK (OpenAPIToolset), Semantic Kernel (kernel.add_plugin_from_openapi), and Microsoft Agent Framework (via the Semantic Kernel plugin pipeline). In the other seven frameworks, the documented pattern is to wrap an HTTP call in a custom tool body or front the API with an MCP server.

RPC

5 · No framework provides a first-class gRPC generator

None of the ten frameworks generates tools from a gRPC, Thrift, or other RPC schema. In every case the documented pattern is to call the RPC client from within an in-process tool body.

PORTABILITY

6 · MCP is the most portable tool-definition surface

An MCP server can be consumed by all ten frameworks via their documented MCP integration. Tool definitions placed inside an MCP server are therefore portable across frameworks without modification; framework-specific tool definitions are not.

Mini-glossary

Terms used above that mean slightly different things in different frameworks.

MCP (Model Context Protocol) — open JSON-RPC protocol for exposing tools, resources, and prompts to LLM agents. See modelcontextprotocol.io.
MCP transport — how the client talks to the server: stdio (server runs as a subprocess) and POST-only streamable-http are current; sse is the deprecated legacy transport retained by some frameworks, and websocket is a LangChain4j extension outside the core protocol.
Agent card (A2A) — a .well-known/agent-card.json document at the remote agent's URL describing its capabilities, skills, auth, and supported modes.
A2A (Agent-to-Agent Protocol) — open standard for one agent calling another over HTTP using the agent-card discovery + JSON-RPC messaging. Cross-framework by design.
OpenAPI toolset / toolkit — a framework-level converter from an OpenAPI 3.x spec to a set of tools, one per operation (or one generic verb-based tool).
RemoteGraph (LangGraph) — proxy object that talks to a graph deployed on LangGraph Platform; behaves identically to a local compiled graph for callers.
RemoteA2aAgent (ADK) — agent class that wraps a remote A2A endpoint; attached to a parent agent's sub_agents= list.
MCPManager (Genkit Go) — top-level container for multiple MCP server connections, with ConnectServer for dynamic add and per-server tool resolution.
ToolProvider (LangChain4j) — interface that supplies a list of tools to AiServices at build or invocation time; MCP is one such provider.
rmcp — the official Rust SDK for MCP; in Rig 0.16+ it's the canonical MCP integration (the older mcp-core is being phased out).
