Model Context Protocol — How It Works, On Your Desktop and In the Cloud

A protocol-level reference for the Model Context Protocol (MCP): the wire model, the two current transports (stdio and Streamable HTTP), the connection lifecycle, the OAuth 2.1 authorization model, and how the same protocol powers both desktop AI applications (Claude Code, VS Code, Cursor) and server-hosted AI agents. Every JSON-RPC example is taken from the official MCP specification revision 2025-11-25.

Spec revision in this paper · 2025-11-25 (current stable). A release candidate for revision 2026-07-28 was locked on May 21, 2026; the final ships July 28, 2026. It is the largest revision since launch and contains breaking changes. The most consequential for this paper:
  • The initialize / notifications/initialized handshake is removed (SEP-2575). Protocol version, client info, and client capabilities now travel in _meta on every request; a new server/discover method fetches server capabilities on demand. §4 of this paper describes the current handshake.
  • The MCP-Session-Id header and protocol-level session are removed (SEP-2567). Any request can land on any server instance — no sticky routing required. §3, §6, §9, and §11 of this paper describe the current session model.
  • New required Streamable HTTP headers: MCP-Protocol-Version, Mcp-Method, and Mcp-Name on every request, so gateways can route without inspecting the body.
  • Roots, Sampling, and Logging capabilities are deprecated (continue to work; replacements documented in the RC notes).
  • Tools' inputSchema / outputSchema are lifted to full JSON Schema 2020-12, with support for oneOf, anyOf, allOf, $ref, and $defs.
  • The Tasks feature graduates out of the core spec into an Extensions track.
This paper will be updated after the 2026-07-28 spec is finalised. Until then, every claim below is verified against the current stable revision 2025-11-25.

1 · The wire model

MCP is an open, JSON-RPC 2.0–based protocol that connects an MCP client (typically an LLM application or agent runtime) to one or more MCP servers (processes that expose tools, resources, and prompts). The protocol is transport-agnostic; the current revision (2025-11-25) standardises two transports: stdio and Streamable HTTP.

Figure 1 · MCP wire model: client and server communicate JSON-RPC 2.0 messages over a transport. The blue arrows show client-initiated requests; the amber dashed arrows show server-initiated responses and notifications.
  1. 1
    Client (host)

    The application that hosts the LLM and orchestrates tool use. Examples in this paper: Claude Code, VS Code (Copilot Chat), Cursor, and any custom agent runtime that links the MCP client library.

  2. 2
    Server

    A separate process (local subprocess or remote service) that exposes tools, resources, and/or prompts. One client maintains one logical connection per server. A client typically connects to several servers concurrently.

  3. 3
    Transport

    Either stdio (server runs as a child process; messages flow through stdin/stdout) or Streamable HTTP (server is a network endpoint reached over HTTP POST, with optional Server-Sent Events for server-initiated messages).

  4. 4
    Messages

    Three JSON-RPC 2.0 message types: requests (have an id, expect a response), responses (match a request by id), and notifications (no id, no response). All messages share a single bidirectional channel.

Source: modelcontextprotocol.io · Specification 2025-11-25 · Architecture · Base Protocol overview · Transports

2 · The stdio transport

Under the stdio transport, the client launches the server as a child process and exchanges newline-delimited JSON-RPC messages over the server's standard input and standard output. The server may write UTF-8 strings to standard error for logging. This is the default transport for local, single-user tools (filesystem access, local databases, local scripts).

Figure 2 · stdio transport: the client spawns the server as a child process. Each JSON-RPC message is a single line of UTF-8 JSON terminated by \n and MUST NOT contain embedded newlines. stderr is reserved for free-form server logs.
  1. 1
    Launch

    The client invokes the server's command with args and an optional env map. The server inherits the client's working directory unless the client overrides it. No network sockets are opened.

  2. 2
    Framing

    Each JSON-RPC message is one UTF-8 line terminated by \n. Embedded newlines are forbidden, so multi-line content must be JSON-escaped. There is no separate header frame; the line itself is the message.

  3. 3
    Logging

    The server MAY write any UTF-8 text to stderr; the client captures and surfaces it for debugging. This is the only out-of-band channel — anything written to stdout MUST be a valid JSON-RPC message.

  4. 4
    Lifecycle

    The connection ends when either process closes its end of the pipes. The client typically sends SIGTERM/SIGKILL to shut down the server cleanly.

Source: modelcontextprotocol.io · Specification 2025-11-25 · Transports

3 · The Streamable HTTP transport

Streamable HTTP is the standardised transport for remote MCP servers. The server exposes a single HTTP endpoint that supports both POST (for client-to-server messages) and GET (for the optional server-initiated message stream). A response to a POST can be either a single JSON object or a Server-Sent Events (SSE) stream, depending on whether the server needs to emit multiple messages in reply.

Figure 3 · Streamable HTTP transport: one HTTP endpoint handles all traffic. Clients POST requests; the server responds with either a single JSON body or an SSE stream of multiple messages. A separate, optional GET opens a channel for server-initiated requests.
  1. 1
    Single endpoint

    The server exposes one path (commonly /mcp). The client sends Accept: application/json, text/event-stream so the server may choose its response format per call.

  2. 2
    Two response shapes

    If the server returns one response, it sends Content-Type: application/json. If it needs to stream multiple messages (e.g. a server-initiated request in the middle of handling a tool call), it returns Content-Type: text/event-stream.

  3. 3
    Sessions

    On initialize, the server MAY return an MCP-Session-Id header. The client echoes that header on subsequent requests to keep them on the same logical session. Session state allows the server to scale horizontally while still routing related calls together.

  4. 4
    Server-initiated stream

    For notifications (e.g. tools/list_changed, progress updates) and server-initiated requests (e.g. sampling), the client opens a long-lived GET against the same endpoint. The server streams messages over SSE.

  5. 5
    Authorization

    Requests carry a Bearer token from the OAuth 2.1 flow described in §6. The server validates the token's audience matches its own URI (RFC 8707 resource indicator) before processing the JSON-RPC envelope.

About the legacy SSE transport. The earlier two-endpoint HTTP+SSE transport from spec revision 2024-11-05 is now deprecated. Servers MAY continue to expose it for backwards compatibility, and clients SHOULD attempt Streamable HTTP first and fall back to the legacy SSE shape only if they receive HTTP 400/404/405 on POST.

4 · Connection lifecycle

Every MCP connection follows the same four-step lifecycle: initialize the connection, acknowledge with the initialized notification, list the server's capabilities, and then invoke tools as needed. The lifecycle is identical for stdio and Streamable HTTP — only the framing differs.

Figure 4 · The MCP lifecycle as a sequence diagram. Blue: client requests. Green: server responses. Amber dashed: notifications (no id, no response). The diagram shows one tool call; in practice phase 3 repeats for every tool the LLM invokes.
  1. 1
    Phase 1 · Initialization

    The client sends initialize with its protocolVersion, supported capabilities, and clientInfo. The server replies with its own protocolVersion, capabilities, and serverInfo. The client then sends a notifications/initialized notification to confirm the connection is ready.

  2. 2
    Phase 2 · Discovery (within the spec's Operation phase)

    The client calls tools/list (and, optionally, prompts/list / resources/list) to discover what the server exposes. Each tool comes with a name, a human-readable description, and a JSON Schema inputSchema that defines its arguments.

  3. 3
    Phase 3 · Invocation (within the spec's Operation phase)

    When the LLM decides to call a tool, the client sends tools/call with the tool's name and arguments. The server returns a content array (typically text blocks, but image, audio, and embedded resources are also defined). For long-running calls, the server MAY emit notifications/progress.

  4. 4
    Notifications

    Throughout the connection, the server can push notifications/tools/list_changed (when the available tool list changes), notifications/resources/.../updated, and notifications/logging/message. Notifications have no id and never receive a response.

  5. 5
    The spec's three formal phases

    The MCP specification names three lifecycle phases: Initialization, Operation, and Shutdown. Phase 1 above maps to Initialization; phases 2 and 3 are both within Operation and are split here for clarity. Shutdown is transport-specific and is not shown.

5 · Pattern A — Desktop AI applications

A desktop AI app (Claude Code, VS Code, Cursor, and several others) ships an MCP client built into the application process. The app reads a configuration file that lists MCP servers; on startup, it spawns each stdio server as a child process and opens HTTP connections to each remote server. Tools from all servers are presented to the LLM as a single combined toolset.

Figure 5 · The desktop pattern: one application process embeds the MCP client library, spawns local stdio servers as children, and opens authenticated HTTPS connections to remote MCP servers. The configuration file lists both kinds together.
  1. 1
    Config-driven

    The application loads a JSON config (location and root key vary by app; see snippets below) that lists every MCP server it should connect to. Servers are typically scoped at three levels: user-wide, workspace/project, and (in Claude Code) enterprise-managed.

  2. 2
    One process, many servers

    Each stdio server is started as a child process. Each remote server is reached over HTTPS. All of them feed tools into the same client; the LLM sees a single combined toolset (with names typically prefixed by server name to avoid collisions).

  3. 3
    Auth lives at the transport

    Remote servers are authenticated per the OAuth 2.1 flow described in §6 — the desktop app stores the access token in the OS keychain and passes it as Authorization: Bearer … on every request.

  4. 4
    Lifecycle is per-connection

    The client repeats initialize → tools/list → tools/call independently for each server. Servers do not see each other; the client merges their tool lists before showing them to the LLM.

Configuration — Claude Code

Claude Code reads .mcp.json at the project root (or ~/.claude.json for user-wide servers). The type field accepts stdio, http, or streamable-http (alias for http). 

{
  "mcpServers": {
    "github": {
      "type": "streamable-http",
      "url": "https://api.githubcopilot.com/mcp/",
      "headers": {
        "Authorization": "Bearer YOUR_TOKEN"
      }
    },
    "my-db": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "@bytebase/dbhub", "--dsn",
               "postgresql://readonly:pass@prod.db.com:5432/analytics"],
      "env": { "DB_TIMEOUT": "30000" }
    }
  }
}

Source: code.claude.com/docs/en/mcp · Connect Claude Code to tools via MCP

Configuration — VS Code (Copilot Chat)

VS Code reads .vscode/mcp.json for workspace-scoped servers (or a user-profile mcp.json for user-wide). The root key is servers (not mcpServers); the type field accepts stdio or http. 

{
  "servers": {
    "github": {
      "type": "http",
      "url": "https://api.githubcopilot.com/mcp/"
    },
    "playwright": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "@microsoft/mcp-server-playwright"]
    }
  }
}

Source: code.visualstudio.com · Copilot · MCP servers

Configuration — Cursor

Cursor reads ~/.cursor/mcp.json (global) or .cursor/mcp.json (project). The root key is mcpServers; if the url field is present, the transport defaults to HTTP. 

{
  "mcpServers": {
    "github": {
      "url": "https://api.githubcopilot.com/mcp/"
    },
    "filesystem": {
      "command": "npx",
      "args": ["-y", "mcp-server-filesystem", "/path/to/project"],
      "env": { "LOG_LEVEL": "info" }
    }
  }
}

Source: cursor.com/docs/mcp

Naming quirks across clients. Claude Code and Cursor use mcpServers; VS Code uses servers. Claude Code's HTTP type is streamable-http (with http accepted as alias); VS Code uses http; Cursor infers HTTP when url is set. All three accept the same stdio fields (command, args, env).

6 · Pattern B — Server-hosted AI agents

In this pattern, an MCP client lives inside an agent runtime running in a container, a serverless function, or a long-lived service. Local stdio servers are uncommon here because the agent process may be ephemeral and may not have a writable filesystem; instead, the agent connects to one or more remote MCP servers over Streamable HTTP. Many remote MCP servers can be hosted on the same cluster as the agent, or with a third party.

Figure 6 · A horizontally-scaled agent service consuming MCP servers. Each replica embeds an MCP client and opens its own connections to internal and third-party servers. MCP-Session-Id lets server-side load balancers pin a logical session to one backend.
  1. 1
    Stateless replicas

    Agent replicas are typically stateless at the process level. Each replica that handles a request opens (or reuses) its own MCP connections. Session affinity is achieved at the MCP layer via MCP-Session-Id rather than at the load balancer.

  2. 2
    Streamable HTTP everywhere

    stdio is rarely usable because the agent process may not have permission to spawn subprocesses, or may be cold-started per request. Streamable HTTP is the default; even MCP servers that originally shipped as stdio are commonly wrapped in a small HTTP front so a hosted agent can reach them.

  3. 3
    Two trust domains

    "Internal" MCP servers (inside the same VPC or cluster) often authenticate with mTLS or short-lived JWTs. "External" MCP servers (third-party vendors) use OAuth 2.1 with per-resource access tokens. The agent runtime is responsible for fetching and refreshing both.

  4. 4
    Tool selection happens in the LLM

    Just like the desktop pattern, all tools from all MCP servers are flattened into the model's tool list at each turn. The choice of which tool to call is the LLM's; the MCP client just routes calls to the right server.

Source: modelcontextprotocol.io · Specification 2025-11-25 · Transports · Session management (MCP-Session-Id semantics) · Authorization (OAuth 2.1 token model). The architectural commentary about stateless replicas, ephemeral runtimes, and trust domains is not in the spec; it describes how MCP is commonly deployed in containerised agent runtimes.

7 · Authorization (Streamable HTTP)

For remote (HTTP) MCP servers, the spec mandates OAuth 2.1 with three RFC profiles: PKCE (mandatory on all clients), Resource Indicators (RFC 8707; tokens are bound to a specific MCP server URI), and Protected Resource Metadata (RFC 9728; clients discover the authorization server from the resource server). Dynamic Client Registration (RFC 7591) is supported for backwards compatibility but Client ID Metadata Documents are now the preferred path.

Figure 7 · OAuth 2.1 + RFC 9728 + RFC 8707 flow. The client probes the MCP server unauthenticated, follows the discovery chain to the authorization server, completes a PKCE-protected authorization code exchange with the target resource indicator, and then makes its authenticated MCP request.
  1. 1
    Discovery (steps 1–4)

    The client makes an unauthenticated request, receives a 401 with a WWW-Authenticate header pointing at the resource metadata document, and fetches that document to learn which authorization server(s) protect this resource.

  2. 2
    Authorization code + PKCE (steps 5–6)

    The client redirects the user to the authorization server with a PKCE code challenge and the resource parameter (RFC 8707) naming the MCP server's URI. After user consent, the authorization server returns an authorization code.

  3. 3
    Token exchange (steps 7–8)

    The client exchanges the code (plus the PKCE verifier) for an access token. The token's audience is bound to the specific MCP server URI; it cannot be replayed against another resource server.

  4. 4
    Authenticated MCP (steps 9–10 and onward)

    The client includes Authorization: Bearer … on every HTTP request to the MCP server. The server validates audience, signature, and scopes before processing the JSON-RPC envelope. On scope failure, the server returns 403 with WWW-Authenticate: Bearer error="insufficient_scope", scope="…" and the client initiates a step-up authorization.

Source: modelcontextprotocol.io · Specification 2025-11-25 · Authorization

8 · Authoring an MCP server

The official MCP SDKs are maintained at modelcontextprotocol/python-sdk and modelcontextprotocol/typescript-sdk. Both ship a high-level API (FastMCP in Python, McpServer in TypeScript) that hides the JSON-RPC plumbing, plus a lower-level API for fine-grained control. The same server code can be served over stdio or Streamable HTTP by choosing a different transport at startup.

Python — FastMCP

Install with pip install mcp. A minimal server exposes one tool and runs over stdio: 

from mcp.server.fastmcp import FastMCP

mcp = FastMCP("greeting-server")

@mcp.tool()
def greet(name: str) -> str:
    """Greet someone by name"""
    return f"Hello, {name}!"

if __name__ == "__main__":
    mcp.run()              # stdio is the default transport

Source: github.com/modelcontextprotocol/python-sdk · README quickstart

To serve the same code over Streamable HTTP, change one line:

if __name__ == "__main__":
    mcp.run(transport="streamable-http", host="127.0.0.1", port=8000)
    # server is now reachable at http://localhost:8000/mcp

Source: gofastmcp.com · Running your server

TypeScript — McpServer

Install with npm install @modelcontextprotocol/sdk zod. A minimal stdio server: 

import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import { z } from "zod";

const server = new McpServer({ name: "greeting-server", version: "1.0.0" });

server.registerTool(
  "greet",
  {
    description: "Greet someone by name",
    inputSchema: z.object({ name: z.string() }),
  },
  async ({ name }) => ({
    content: [{ type: "text", text: `Hello, ${name}!` }],
  }),
);

const transport = new StdioServerTransport();
await server.connect(transport);

Source: github.com/modelcontextprotocol/typescript-sdk · README quickstart

The Streamable HTTP variant swaps the transport import and provides network options:

import { StreamableHTTPServerTransport }
  from "@modelcontextprotocol/sdk/server/streamableHttp.js";

const transport = new StreamableHTTPServerTransport({ /* options */ });
await server.connect(transport);
// Mount the transport's HTTP handler on your web framework (Express, Hono, …).

Source: github.com/modelcontextprotocol/typescript-sdk · docs/server.md · Streamable HTTP transport

The tool function signature is the schema. In both SDKs, the tool's parameter types are also its JSON Schema inputSchema. Python derives the schema from type hints and docstring; TypeScript derives it from the Zod schema. The result is what the model sees in the tools/list response.

9 · Side-by-side · stdio vs Streamable HTTP

10 · Summary observations

Six factual observations drawn from the spec and current SDK behaviour.

PROTOCOL

1 · MCP is a thin JSON-RPC 2.0 protocol

The wire format is plain JSON-RPC. There are three message types (request, response, notification), four core methods for tools (initialize, notifications/initialized, tools/list, tools/call), and a small set of capability flags negotiated in the handshake.

TRANSPORTS

2 · Two transports are standardised; the legacy SSE one is deprecated

The current spec (revision 2025-11-25) defines stdio and Streamable HTTP. The earlier two-endpoint HTTP+SSE transport remains documented for backwards compatibility only.

DESKTOP

3 · Desktop apps merge tools from many servers

Claude Code, VS Code, and Cursor each load a JSON config file (.mcp.json / .vscode/mcp.json / .cursor/mcp.json) listing stdio and remote servers. The client merges their tools into one combined list for the LLM.

HOSTED

4 · Hosted agents use HTTP almost exclusively

Server-hosted agent runtimes prefer Streamable HTTP because container/serverless environments often cannot spawn subprocesses, share filesystem state, or persist between invocations. Session affinity for multi-call interactions is achieved via the MCP-Session-Id header rather than load-balancer stickiness.

AUTH

5 · The HTTP transport mandates OAuth 2.1 + PKCE + resource indicators

Discovery uses Protected Resource Metadata (RFC 9728); authorization uses OAuth 2.1 with PKCE; tokens are scoped to a specific MCP server URI via Resource Indicators (RFC 8707). Dynamic Client Registration (RFC 7591) is supported for backwards compatibility; Client ID Metadata Documents are the preferred registration path going forward.

SDKS

6 · The official SDKs hide the JSON-RPC plumbing

FastMCP in Python and McpServer in TypeScript reduce a tool-exposing server to a class, a decorator/registerTool call, and a run()/connect() entry point. Switching between stdio and Streamable HTTP is a one-line change in both SDKs.

Sources for the six observations above, in order: Base Protocol · Transports · client docs cited in §5 (Claude Code, VS Code, Cursor) · Session Management · Authorization · SDK docs cited in §8 (Python, TypeScript).

11 · Mini-glossary

Terms used throughout this paper.

MCP — Model Context Protocol; an open JSON-RPC 2.0 protocol for connecting LLM applications to tool servers. Spec at modelcontextprotocol.io.
Client / Host — the application that hosts the LLM and the MCP client library (Claude Code, VS Code, a hosted agent runtime).
Server — a process that exposes tools, resources, and/or prompts to MCP clients. Can be a local subprocess (stdio) or a network service (HTTP).
Tool — a callable exposed by a server, described by name, description, and a JSON Schema inputSchema. Invoked via tools/call.
Resource — a piece of read-only content (file, document, query result) the server can supply. Listed via resources/list and fetched via resources/read.
Prompt — a parameterised template the server exposes that the client can render and present to the user.
stdio transport — server runs as a child process; messages flow over newline-delimited JSON on stdin/stdout.
Streamable HTTP transport — server exposes one HTTP endpoint; clients POST requests; responses are JSON or SSE; a separate GET opens a server-to-client SSE stream.
MCP-Session-Id — header issued in the initialize response that the client echoes on every subsequent request to keep them on the same logical session.
FastMCP — high-level Python SDK API; decorator-based server authoring.
McpServer — high-level TypeScript SDK API; registerTool-based server authoring with Zod schemas.
RFC 8707 (Resource Indicators) — OAuth 2.0 extension that binds an access token to a specific resource server, preventing token replay.
RFC 9728 (Protected Resource Metadata) — discovery document at /.well-known/oauth-protected-resource that tells clients which authorization server protects a resource.
PKCE — Proof Key for Code Exchange (RFC 7636); mandatory in OAuth 2.1 to prevent authorization code interception.

All MCP-specific term definitions above are taken from the MCP Specification 2025-11-25 (Base Protocol, Transports, Lifecycle, Authorization, and Server / Tools sub-pages). RFC numbers refer to the published IETF documents.
