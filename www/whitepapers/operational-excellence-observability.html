Observability

An agent in production is opaque by default. The model picks tools and arguments based on reasoning you cannot directly inspect; tools call other services that themselves call models; a single user request fans out into a tree of LLM calls, retries, and database hits. Observability is what makes this tree legible — what tracing surfaces does each framework ship, how does it integrate with OpenTelemetry, what metrics does it emit, and what vendor dashboards can you point it at? This chapter walks through each surface in plain language, then catalogs the concrete primitives across ten frameworks spanning Python, TypeScript, .NET, Java, Go, and Rust.

The ten frameworks under comparison: LangChain, LangGraph, CrewAI, Google ADK, Microsoft Semantic Kernel (Python), Mastra (TypeScript), Microsoft Agent Framework (.NET), LangChain4j (Java), Genkit (Go), and Rig (Rust).

1Tracing surfaces & span hierarchy

A trace is the structured record of an agent run — who called whom, in what order, and how long each step took. The shape of the trace determines what kind of debugging you can do after the fact: a flat list of "events" tells you what happened; a properly nested span hierarchy lets you see why a particular tool call took eight seconds when the rest of the run took two.

What this looks like in practice

A user asks your agent a question. Behind the scenes the run produces: one outer "agent run" span, three "model call" spans (one per reasoning step), four "tool call" spans (search, lookup, search again, summarise), and one final "agent response" span. With a properly nested trace, your dashboard renders this as a waterfall: you can see the third model call took 6 seconds, and inside it the only thing that ran was a single tool call that took 5.8 seconds — so the slowdown was the downstream service, not the LLM. Without a properly nested trace, you have a flat list of timestamped events and have to reconstruct the parent-child relationship by hand.

Frameworks differ on three axes here: (1) do they emit spans at all out of the box, (2) what's the span hierarchy (flat events, or modelled run → step → tool / agent → model call), and (3) do they emit through OpenTelemetry's standard APIs so any OTel-compatible backend can ingest them, or through a framework-specific callback you have to translate yourself.

What this means in practice

Six frameworks (CrewAI, ADK, Semantic Kernel, Mastra, MS Agent Framework, Genkit Go) give you usable spans on day one — pick a backend, wire an exporter, you're done. Three require meaningful additional work: LangChain and LangGraph need LangSmith or a custom translator to turn callback events into spans; LangChain4j needs the Micrometer adapter to turn listener events into anything observable. Rig sits at the far end — you get structured log events and nothing else; agent-level tracing is something you build.

Trace nesting matters less than it sounds when reading source code, but it matters a lot when reading a dashboard. ADK, Mastra, and Genkit Go produce naturally nested traces because their flows nest (ADK uses start_as_current_span inside with blocks). SK and MS Agent Framework give you a clean two-tier view. CrewAI emits spans named like a hierarchy (Crew Execution, Task Execution, Tool Usage) but they aren't actually nested — they show up as separate top-level spans you can filter by name. The flat-events + downstream-reassembly pattern (LangChain, LangGraph, LangChain4j) works once your tracer is configured but means more steps before the first useful waterfall renders.

2OpenTelemetry adoption

OpenTelemetry is the de facto standard for distributed tracing — vendor-neutral APIs and semantic conventions that let you swap dashboards without rewriting instrumentation. For agents specifically, the Gen AI semantic-convention working group has standardised attribute names like gen_ai.client.token.usage and gen_ai.operation.name. Eight of the ten frameworks ship native or first-party OTel; two integrate via plugins.

What this looks like in practice

Your platform team standardised on Datadog APM. A new team wants to ship an agent feature and they're using a different framework than the rest of the company. With OTel as a native dependency, the new team gets working dashboards on day one — Datadog's OTel-compatible ingestion sees the spans, recognises the gen_ai.* attributes, and renders token-usage and latency panels automatically. Without OTel, the team writes a translator from the framework's callback interface to Datadog's API, maintains it forever, and inevitably discovers that retries / nested calls / streaming aren't quite right in the translation.

"Native OTel" means the framework imports the OTel library directly, declares spans through it, and follows the Gen AI semantic conventions. "First-party plugin" means the framework ships a separate package that bridges its own callback model to OTel. "Plugin" means OTel is reachable but the developer wires it. "Absent" means there's no official path and you have to write your own.

What this means in practice

Six frameworks (CrewAI, ADK, SK, Mastra, MS Agent Framework, Genkit Go) work directly with any OTel-compatible backend the moment you register an exporter. LangChain and LangGraph route through LangSmith; LangChain4j routes through Micrometer; Rig routes through the Rust tracing-opentelemetry bridge. All three of those routes work, but each adds a layer of translation you have to set up and maintain.

On standard attribute names — the ones a Datadog or Grafana Gen AI dashboard expects — ADK, MS Agent Framework, Semantic Kernel, and LangChain4j are the most aligned. Mastra, CrewAI, and Genkit Go follow the conventions partially and add their own. LangChain, LangGraph, and Rig don't follow them at all without extra work. If you're picking a framework specifically because you want existing dashboards to "just work," the first group is the safest starting point.

3Metrics emission

Tracing tells you what happened in one specific run. Metrics tell you what's been happening across millions of runs — token usage rates, p99 latency, error counts per tenant. Six of the ten frameworks emit first-class metrics out of the box; the others surface the data through traces or callbacks but don't aggregate it.

What this looks like in practice

It's Tuesday morning. Your CFO asks why the OpenAI bill spiked 40% over the weekend. With first-class metrics emission, you open Grafana, filter the gen_ai.client.token.usage histogram by tenant and model, and within a minute you see one customer ramped their usage of GPT-4o-mini by 5×. Without metrics emission, you're querying every individual trace, summing token counts by hand, and presenting an estimate three days later.

Out-of-the-box metrics matter because retrofitting them after the fact is laborious. A framework that ships metrics with sensible defaults (token usage as a histogram, not a counter; tagged with model and operation; emitted at the chat-client layer not the agent layer) gives you a running production view from day one.

LangChain, LangGraph, and Rig don't aggregate metrics out of the box: you either route through their canonical product (LangSmith for the LangChain family) or build the metrics layer yourself.

4Structured logging

Logs are the third leg of the observability tripod, alongside traces and metrics. The question isn't whether the framework writes logs — they all do — but whether those logs are structured (key-value pairs you can filter on in your log search) or plain text you have to grep. The shape of the logging layer also tells you how it integrates with your host language's standard library: Python's logging, Go's slog, .NET's ILogger, Rust's tracing, and so on.

What this looks like in practice

A user reports their agent gave a wrong answer. With structured logs, you search your log aggregator for {trace_id: "abc123"}, get every log line from that run in chronological order, and see the model's tool selection and the tool's response. With plain-text logs, you have an approximate timestamp and a transcript of free-form lines — you spend half an hour grepping by the user's question phrase and stitching together what happened.

The defining feature is correlation: every log line should carry a trace ID so it can be joined back to the trace and the metrics. Frameworks that use the host language's modern structured logging library (slog in Go, ILogger in .NET, tracing in Rust) get this for free; frameworks that use older logging surfaces (Python's standard logging module, Java's SLF4J without context) require the developer to propagate trace IDs manually.

LangChain, LangGraph, and CrewAI default to Python's plain logging module and require manual trace-ID propagation. LangChain4j defers entirely to host configuration — you get whatever Spring Boot or Quarkus is set up to do.

5Vendor integrations

"Open standards" sounds good in principle, but in production you almost always want a pre-built integration with whatever observability vendor your team has already adopted. The frameworks vary wildly here: Mastra ships nine vendor integrations in-tree; LangChain ships one (LangSmith); Rig ships none and expects you to use the OTel ecosystem.

What this looks like in practice

Your team standardised on Langfuse for prompt experimentation and Datadog for production APM. With a framework that ships both integrations, the agent's traces show up in both dashboards on day one — the framework knows how to translate its internal spans into each vendor's format. With a framework that ships only its own dashboard (e.g. LangSmith for LangChain), getting traces into Langfuse means writing or maintaining a bridge yourself, and you'll discover edge cases like streaming or partial-tool-call spans aren't quite right.

The number and breadth of in-tree integrations is also a signal of where each framework's contributors come from. Mastra's nine vendors include both observability SaaS (Langfuse, LangSmith, Datadog) and AI-eval platforms (Arize, BrainTrust). LangChain leans on its own LangSmith product. CrewAI ships a configurable OTLP endpoint instead of dedicated integrations. Rig leans on the broader Rust + OTel ecosystem.

What this means in practice

Mastra and LangChain4j are the two extremes — Mastra ships nine specific vendor integrations covering observability and AI-eval tooling; LangChain4j ships zero agent-specific integrations but inherits Micrometer's enormous vendor reach. Most frameworks ship one or two cloud-vendor-specific integrations (Cloud Trace, Application Insights, LangSmith) and expect you to wire generic OTel for anything else. CrewAI and Rig are at the other end: neither ships dedicated vendor integrations and both rely entirely on OTel as the integration layer.

At a glance

Source-grounded observations on observability surfaces across the ten frameworks.

OTEL

1 · OTel is now table stakes

Six frameworks ship direct OTel SDK dependencies: CrewAI, ADK, Semantic Kernel, Mastra, MS Agent Framework, Genkit Go. The other four reach OTel through a bridge — LangChain4j via Micrometer, Rig via tracing-opentelemetry, LangChain and LangGraph via LangSmith. Every framework gets there; only the wiring effort differs.

SEMCONV

2 · Gen AI semantic conventions are the unifier

Frameworks emitting gen_ai.client.token.usage and Gen AI attributes: ADK (_experimental_semconv.py), MS Agent Framework (OpenTelemetryConsts.cs v1.37), SK, LangChain4j (Micrometer OTelGenAiAttributes). Means a Datadog or Grafana dashboard built once works across these frameworks unchanged.

SPANS

3 · Properly nested traces only ship in three frameworks

ADK and Genkit Go produce nested traces via start_as_current_span inside with blocks; Mastra's flow steps roll up under the agent run. MS Agent Framework's OpenTelemetryAgent gives a two-level wrap. CrewAI emits descriptively named spans (Crew Execution, Task Execution, Tool Usage) but as flat top-level events, not parent-child children. Rig has no agent-level span concept.

METRICS

4 · First-class metrics emission ships in six

ADK (_metrics.py), Semantic Kernel (OTel Meter), Mastra (vendor packages), MS Agent Framework (OpenTelemetryChatClient token + latency), LangChain4j (MicrometerMetricsChatModelListener), and Genkit Go (OTel metrics API). CrewAI surfaces the data through span attributes — your backend aggregates. LangChain, LangGraph, and Rig don't aggregate at all.

LOGGING

5 · Structured logging tracks the host language

Frameworks using modern structured logging by default: ADK and SK (OTel logs), Mastra (custom structured logger), MS Agent Framework (ILogger), Genkit Go (log/slog), Rig (tracing events). LangChain, LangGraph, CrewAI default to plain Python logging; LangChain4j defers to host SLF4J/Log4j config.

VENDORS

6 · Mastra ships nine in-tree integrations

Mastra: LangSmith, Langfuse, Datadog, Arize, BrainTrust, Arthur, PostHog, Sentry, ClickHouse. LangChain ships one (LangSmith); ADK and Genkit ship Google Cloud; SK and MS Agent Framework ship Application Insights; CrewAI ships only a configurable OTLP endpoint; LangChain4j leans on Micrometer's vendor reach; Rig ships none in-tree.
