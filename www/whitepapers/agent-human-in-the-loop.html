Human-in-the-Loop in AI Agent Frameworks

How LangChain, LangGraph, CrewAI, Google ADK, and Microsoft Semantic Kernel let a person step into the agent loop — to approve a tool call, edit a plan, sign off on the final answer, or own a long-running decision the agent simply cannot make alone.

The four places a human can step in

Strip away the framework labels and there are really only four moments in an agent's life where a human can — or must — be in the loop. Every framework in this deck supports some subset of these, with very different durability and developer-experience trade-offs.

1Tool-call approval
The LLM has picked a tool and arguments. Before the tool runs, a human is shown the call and may approve, edit, or reject. Used for irreversible or expensive actions (send email, place order, run shell).
2Mid-run pause + resume
The agent is mid-flight. It hits a checkpoint — explicitly via an interrupt() call, or because the framework was told "always pause before this step." State is persisted; a human responds at their leisure; the run resumes.
3Final-output review
The agent has produced a final answer (or draft email, or report). A human reviews and approves it before it leaves the building. Often plain pause-before-end.
4Long-running async wait
The agent calls a "tool" that is really a human inbox: an approval queue, a Slack message, a manual data-entry task. The framework needs to release the run and accept a callback hours or days later — without losing context.

How each framework actually does it

Each card: one big diagram of the framework's HITL machinery, then the four-pattern coverage and a code-grounded explanation underneath.

Lc

LangChain · the classic AgentExecutor

HITL is bolted on via callback handlers and "ask the human" tools — synchronous, in-process.
"Wrap tools in a callback that prompts y/n. Or hand the agent a 'Human' tool and let it ask."

How HITL works

LangChain has no first-class pause/resume primitive in AgentExecutor. Two patterns are common:

  • Callback approval — register HumanApprovalCallbackHandler (from langchain_community.callbacks.human). Its on_tool_start hook prints the proposed tool call and waits for a y/n; rejection raises an exception that the executor surfaces as a tool error.
  • "Human" as a tool — add a HumanInputRun tool to the agent's tool list. The LLM can choose to call it; the tool runs input() (or any custom prompt callable) to fetch a string from the user.

Both run synchronously, in-process. The agent thread is blocked while the terminal (or your custom callable) waits.

Pattern coverage

1 · Tool approval

Yes, via HumanApprovalCallbackHandler's on_tool_start hook.

2 · Pause + resume

No native primitive. The while loop blocks; restarting the process loses state.

3 · Final-output review

No built-in. You'd wrap the executor or post-process its output yourself.

4 · Long-running async

Possible only if your "Human" tool returns a future and you orchestrate the wait — not framework-managed.

Lg

LangGraph · interrupt() + checkpointer = durable HITL

The only framework here with a true pause/resume primitive whose state survives a process restart.
"Call interrupt() anywhere in any node. Persist state via the checkpointer. Resume hours later with Command(resume=value)."

How HITL works

LangGraph treats HITL as a first-class control-flow primitive. Anywhere in any node you can call interrupt(value) — it raises a GraphInterrupt, LangGraph snapshots the entire graph state via the configured checkpointer, and the value is surfaced to the calling client. A separate process — minutes, hours, or days later — can call the graph back with Command(resume=human_response); the runtime loads the snapshot and re-executes the node from the top, this time with the human's value returned by interrupt.

For "always pause before this node" semantics, compile the graph with interrupt_before=["tools"] or interrupt_after=["agent"]; this is how you do tool approval and final-output review without changing node code.

The HumanInterrupt typed dict — currently in langgraph.prebuilt.interrupt with a deprecation note that it will move to langchain.agents.interrupt — gives you a structured envelope (accept · ignore · respond · edit) that UIs can render consistently.

Pattern coverage

1 · Tool approval

interrupt_before=["tools"] on compile, or call interrupt() inside a custom tool node.

2 · Pause + resume

The native pattern. Pause is durable thanks to the checkpointer; resume via Command(resume=...).

3 · Final-output review

interrupt_after=["agent"] or call interrupt(draft) in a final node before return.

4 · Long-running async

Yes — checkpointer makes the wait survive process restarts. Approval can come from a totally different service.

Cr

CrewAI · task.human_input=True

A flag on the Task. After the agent finishes, a HumanInputProvider takes over and iterates feedback rounds.
"Set a flag on the Task. The agent runs. Its answer is shown to the human. Empty input = accept. Anything else = re-run with that as feedback."

How HITL works

CrewAI's HITL is a per-task flag: Task(..., human_input=True). After CrewAgentExecutor._invoke_loop() returns an AgentFinish, the executor checks self.ask_for_human_input; if true, it calls _handle_human_feedback(), which delegates to a HumanInputProvider (the default SyncHumanInputProvider uses an input() prompt).

The provider runs a while ask_for_human_input loop: prompt for feedback, inject the feedback as a message, re-invoke the agent's loop, repeat. Empty feedback ends the cycle and the latest answer is the task's output. An async path (handle_feedback_async) exists for non-blocking I/O but still keeps the agent's loop in-process.

Pattern coverage

1 · Tool approval

No per-tool approval primitive. You'd wrap the tool yourself.

2 · Pause + resume

No durable pause; the provider blocks the in-process agent loop until input arrives.

3 · Final-output review

Native — this is exactly what human_input=True does, with iterate-on-feedback built in.

4 · Long-running async

The async provider helps, but state is in memory; a process restart loses it unless you persist out of band.

Ad

Google ADK · request_confirmation + long-running tools

Two complementary mechanisms: tool-call confirmation, and tools that release the run and resume on callback.
"Two HITL channels: a confirmation request side-call for tool approvals, and 'long-running' tools that release the run and resume on callback."

How HITL works

Tool-call confirmation. Mark a tool to require confirmation; the request_confirmation request processor (in flows/llm_flows/request_confirmation.py) intercepts the call, emits a special adk_request_confirmation function call to the client carrying a ToolConfirmation envelope (confirmed, payload, hint). The client surfaces it to the human; their decision comes back as a function response and the original call either proceeds or is dropped.

Long-running tools. A LongRunningFunctionTool (or any tool with is_long_running=True) returns to the framework without a final result. ADK records the function_call_id in the Session as a pending event and releases the run. Whenever the external system (queue worker, ticketing tool, human via UI) is ready it sends a function response carrying the same id, and the agent resumes from that point. The built-in get_user_choice tool is implemented exactly this way.

Pattern coverage

1 · Tool approval

Native via request_confirmation + ToolConfirmation (currently @experimental).

2 · Pause + resume

Achievable via long-running tools — the run pauses and resumes on a function-response callback.

3 · Final-output review

No first-class hook, but easy to model as a long-running "review" tool the agent must call before finishing.

4 · Long-running async

Native. Persistence depends on which SessionService you use (in-memory vs. database).

Sk

Microsoft Semantic Kernel · auto-function-invocation filters

A filter sits in front of every plugin call the kernel auto-invokes — that's the HITL hook.
"Register a filter on the kernel. Every auto-invoked function passes through it. Approve, mutate, or terminate."

How HITL works

When FunctionChoiceBehavior.Auto is in effect, the kernel — not your code — invokes plugin functions on the model's behalf. The hook is a filter: register one with kernel.add_filter(FilterTypes.AUTO_FUNCTION_INVOCATION, my_filter). The filter is async middleware that receives an AutoFunctionInvocationContext (with the function_call_content, the chat_history, the request/function index in the loop, etc.) and decides what happens next.

Inside the filter you can: prompt a human (anything await-able will do — aioconsole.ainput, an HTTP wait, a queue subscriber); mutate the arguments before forwarding; set context.function_result to short-circuit the call entirely; or set context.terminate = True to stop the whole function-call loop. Calling await next(context) lets the call proceed.

Pattern coverage

1 · Tool approval

Native — auto-function-invocation filter is exactly this. Approve, mutate, or replace the result.

2 · Pause + resume

Process-level only — the filter awaits, but state is in memory. Restarting kills it.

3 · Final-output review

Done outside the kernel: review the agent's AgentResponseItem before forwarding. No built-in hook.

4 · Long-running async

Possible only if your filter integrates with a durable queue you own. Nothing built in.

Architect's cheat sheet

If HITL is non-negotiable in your domain (regulated industries, high-blast-radius actions, content moderation), the framework choice has consequences.

DURABILITY

1 · The hard question is "can the agent wait days?"

Most HITL "support" is really an input() blocking the agent thread. Only LangGraph (checkpointer) and ADK (long-running tool + persistent SessionService) survive a process restart with the run intact.

VOCABULARY

2 · Structured human responses are worth a lot

LangGraph's HumanInterrupt (accept · ignore · respond · edit) and ADK's ToolConfirmation are typed envelopes you can render consistently across UIs. CrewAI is free-text only; LangChain is y/n. UI-side reusability follows.

GRANULARITY

3 · Per-tool vs. per-step vs. per-task

ADK and SK gate at the tool / function level. LangGraph gates at the node / super-step level. CrewAI gates at the task level. Match the gate granularity to where your blast-radius lives.

DX

4 · Easiest path to "yes/no on every tool"

LangGraph: one line at compile (interrupt_before=["tools"]). ADK: mark tools with require_confirmation. SK: a 10-line filter that input()s. LangChain: register the callback. CrewAI: roll your own.

DX

5 · Easiest path to "review the final answer"

CrewAI wins here — human_input=True on the last task. LangGraph is close (interrupt_after=["agent"]). The others need wrappers.

RISK

6 · Don't conflate "filter that can prompt" with "real HITL"

A filter that awaits input() works on a laptop. Production HITL needs durability (graph state survives restarts), routability (any of N humans can answer), and auditability (who clicked yes?). Most of that is your problem regardless of the framework — but the framework should at least not make it impossible.
