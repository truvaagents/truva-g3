Too Big to Read: How TruvaG3 Fits a Megabyte of Results Back Into the Prompt

Ask an AI agent to dig through a system's logs and metrics and one tool call can return a megabyte of JSON, another a few hundred log streams. That result does not just get stored — it has to go back into an LLM, twice: once for the agent to decide what to do next, and once to write the final answer. Put the raw payload in a prompt and you can blow the context window or, worse, quietly degrade the model's reasoning. This is TruvaG3's[1] answer: result compaction — three layers, two prompt paths, and one invariant that makes throwing data away safe. It runs automatically, and everything below was checked against the source.

The result that doesn't fit

This whole article is built on one real run, so let's start there. TruvaG3[1] is an open-source framework for building LLM agents — programs that answer a request by writing a plan, calling tools to gather data, and then using an LLM to turn what came back into a final answer. One of its bundled example agents[4], a DevOps assistant[5], was asked a broad, data-hungry question — "Analyze the cluster and the pods health. Tell me if there are any issues in the services by checking the logs and other data points that may reveal the details. I want the analysis from the last 6 hours of data." To answer it, the agent wrote a plan and made 28 tool calls (it calls each one a step), grouped into 4 rounds of plan-then-run (each round is a phase), using three tools: devops-tool (which runs kubectl, the Kubernetes command-line tool), devops-observability-tool (which fetches logs from Loki, a log database), and prometheus-query-tool (which reads metrics).

The results those tools returned were not small. Together they came to 2.71 MB, and the single biggest — one kubectl dump — was 855 KB on its own; a dozen of the twenty-eight were large enough to need compaction. None of this is unusual — a single broad question routinely returns results this large.

Here is the problem. A step's result is not the end of the line — the plan is not finished. That result has to be read back by an LLM so the run can continue: the agent needs to see what happened in order to plan its next steps, and, at the very end, an LLM call has to read the results to write the final answer (this last call is the one TruvaG3 calls synthesis). Either way, a megabyte of kubectl output has to fit into a prompt — and a prompt has two ceilings, not one.

The first ceiling is hard and obvious: exceed the model's context window and the call simply fails. The second is softer, and it is the one that actually causes the trouble. Reasoning accuracy degrades well before the context is full — the framework's own effective-prompts research[6] shows accuracy on a controlled task falling from roughly 0.92 to 0.68 as inputs grow into the low thousands of tokens. A prompt stuffed with raw payload is not just risky; it is a prompt that reasons worse. The model has to find the two log lines that matter among the two hundred it was handed, and every irrelevant kilobyte makes that harder.

Result compaction is the framework's answer: shrink each result to fit a budget while preserving the signal the model actually needs — and do it automatically, so the people writing agents never have to think about it. Any agent connected to an LLM gets it out of the box; there is nothing to opt into. The payoff, in this run: those 2.71 MB of raw results — roughly 812,000 tokens if you fed them into a prompt whole — were compacted into a synthesis prompt of just 25,090 tokens, and 87% of all the token-reading happened on a cheap "fast" model, leaving the expensive reasoning model to see only the compacted result. Where synthesis sits: the life of a query

That run has a shape, and it is worth seeing before we open up the compaction itself — because the word "synthesis" only makes sense once you know where it sits. A TruvaG3 agent answers a request as a short lifecycle, and nearly every stage is an LLM call. The planner picks tools and writes a plan; the executor runs the steps, and this is the one place the large data is born — a tool returns a result. Completed results are kept whole, in memory. Then, while the plan still has phases to go, the planner re-reads those results and plans the next one (continuation, or "replan"); when the plan is finished, one last AI phase — synthesis — turns the results into the answer.

The picture makes the two facts this whole article rests on visible at a glance. First, the data is born in exactly one place — step execution — and everything after it is a consumer. Second, of those consumers, exactly two are AI phases that must read whole step results back into a prompt: the continuation planner between phases (the "replan" path) and the synthesizer at the very end (the "terminal" path). Those two hand-offs are what the rest of this piece is about. The other LLM calls in the run — choosing which tools to use, writing the plan, and micro-resolution (filling in a step's inputs from an earlier step's result) — either produce only small text or read a single result through the same deterministic floor, so they don't drive the design.

Two paths back into the model

The key to the whole design is a distinction the guide makes up front: a result is compacted differently depending on where it is headed. There are exactly two prompt paths for a step result, and they want completely different things from it.

The first is synthesis — the final-answer prompt. Here the model is writing prose for the user, so it wants meaning: of these two hundred log lines, which ones actually bear on the question? The second is continuation planning — the prompt used between phases when the planner re-reads the completed steps to decide what to do next. This is the "replan" path, and it is subtly different: the planner does not need the values in a result at all. It needs the result's shape — enough to reference a field in the next step and to avoid re-issuing work it has already done.

Three mechanisms serve those two paths, and it is worth naming them before we walk each one. Result trimming (the StructuralTrimmer) is a deterministic, LLM-free floor. Result distillation (the LLMDistiller) is the LLM-first primary path for synthesis. Continuation digests are the structure-only skeletons for the planning path. The guide lays them out as a grid, and it maps cleanly onto the code:

LayerRuns onLLM?What it produces

The invariant that makes forgetting safe

Before any of the shrinking, one property has to be true, or the whole scheme is reckless: compaction only ever changes what the LLM sees in a given prompt. The complete, untouched result stays in memory: the orchestrator — the component that runs the plan-and-execute loop — keeps every step's full result. This is not a detail; it is the foundation the whole design rests on.

Here is why it matters. A TruvaG3 plan wires steps together with templates — a later step can say {{step-9.response.data.streams}} to feed the entire result of step 9 into a tool call. Those templates resolve against the full value at execution time, out of memory, not out of whatever summary a prompt happened to show. So the planner can look at a six-hundred-byte skeleton that merely tells it "there's a data.streams array of 200 entries," write a step that references it, and the executor will bind all 200 entries at run time. The summary is a view for reasoning; it is never a replacement for the data. That is exactly what makes lossy compaction safe: you are never deleting anything the run might still need — you are only deciding how many prompt tokens to spend showing it to a model.

On top of that invariant sit three design principles that recur in every layer of the code:

  • Fail-open, always. On failure, every layer falls back to a smaller, safe result rather than failing the request. No AIClient? Fall back to the deterministic floor. Cache error? Recompute. Deadline hit? Return what finished, with an honest note. A compaction step can never be the reason a user's request errors out.
  • Default-on. You get sensible compaction out of the box. You opt out, or you tune it; you never have to opt in.
  • Prompt-only. The full result is never lost — see above. Every summary is a lens, and the framework treats it as one.

Layer 1: the structural floor

The bottom layer is the StructuralTrimmer — deterministic, LLM-free, and therefore fast, free, and incapable of failing. It never calls a model, which is precisely why it can serve as the fail-open floor for everything above it. When distillation is switched off, or there is no AIClient, or an LLM call times out, this is what runs.

What it does is whole-unit structural selection to fit a byte budget. It inventories the result's fields and array items, then keeps whole units in breadth-first order — shallowest first, and largest-first within a depth — descending into a unit only when it is too big to keep whole. A field that fits is kept intact rather than picked apart. Units that do not fit are dropped and counted (FieldsDropped). In the code, this is a sort by depth ascending, then by size descending; the comment calls it the "whole-unit guard," and it is what keeps the output structurally coherent instead of a scattering of disconnected fragments.

Two details are worth pinning down because they are easy to get wrong. First, a top-level array is filled from its head, but a nested array is first capped to its first 500 items (maxArrayInventoryItems = 500) and then run through the same whole-unit sort — so its kept items are not a strict head sample. Second, the primary cut is not a relevance ranking. Relevance scoring exists in the trimmer, but it only drives a secondary backfill pass and key ordering; picking the query-relevant content is distillation's job, one layer up. The trimmer preserves shape, not meaning.

On the JSON path, the kept payload is valid JSON, but the trimmer appends a short plain-text annotation after it — so the returned string is a JSON body followed by a note, not a pure-JSON document. A non-JSON input (logs, plain text) skips structure entirely and is reduced as plain text — keyword-scored sentence selection, not a blind head cut — with the same kind of annotation. And there is a safety floor beneath the floor: if a trim keeps under 5% of the source (degenerateKeptRatio = 0.05), the note escalates to [severely reduced … treat anything NOT shown as UNKNOWN], because at that point the sample is no longer representative and the synthesizer must not read absence into it.

The trimmer runs in several places, each with its own budget. The two that matter most for synthesis are a 16 KB per-result cap and a 32 KB total-prompt cap. One default is deliberately surprising:

BudgetDefaultPurpose
Per-result cap16 KBceiling per result when several share one synthesis prompt
Total prompt32 KBall results combined in one synthesis prompt
Micro-resolution source64 KBsource data fed to parameter resolution / semantic retry
Agent input (tool→tool)0 — no capone tool's output feeding another tool's input

That last row is the surprising one, and it is a design statement. When one tool's output feeds another tool's input, the downstream tool gets the full upstream result by default — no cap. The reasoning is fidelity-first: a tool consuming data programmatically usually needs all of it, unlike a model consuming it to reason. Compaction is for prompts, not for pipelines. (You can set a cap or supply a custom processor if you specifically want to bound inter-tool payloads — but you have to ask for it.)

Layer 2: distillation, the synthesis path

Structural trimming preserves shape, but for the final answer you usually want meaning. That is what distillation does, and it is the primary compaction path for the synthesis prompt. It is on by default; it kicks in when a result exceeds the 16 KB DistillThreshold and the agent is connected to an LLM. When it runs, it is a two-stage pipeline.

Stage 1 — structural pre-filter. The StructuralTrimmer from Layer 1 reduces the raw result to the 128 KB PreFilterBudget, so the model is never handed the entire multi-megabyte payload. Stage 2 — LLM distill. A fast model — Haiku, gpt-4.1-mini, or gemini-flash-lite, reached through the portable fast alias — summarizes the pre-filtered content down to roughly the 4 KB TargetSize, conditioned on the user's original query and the step's task so it keeps what is relevant to both.

The distiller's system prompt is what makes the 4 KB trustworthy. It does not tell the model "summarize this." It tells the model it is a selector, not a paraphraser: first decide whether the data is evidence (records, log lines, rows, search hits) or narrative (prose). For evidence, copy the matching units verbatim — exact text, identifiers, primary keys, timestamps, numeric values, byte for byte. Only narrative gets paraphrased, and even then identifiers and numbers are preserved exactly. If nothing is relevant, the model must emit a specific sentinel (No matching entries found) rather than inventing an answer, and it may state that something is absent only after inspecting the whole input.

You can watch that play out on a real result from the run[9]. Step-16 asked for error logs from two services and got back 97.7 KB of nested, escaped Loki JSON — this is the shape the fast model had to read (excerpt):

The other half of that contract is knowing when there is nothing to report. Step-13 went hunting for OOMKilled, CrashLoopBackOff, and pod-eviction events across every service. The 39 KB of logs that came back were only advisory debug chatter — recommendations about monitoring, not actual incidents — so rather than invent a failure, the model said exactly that (its full output, 0.6 KB):

Those two outputs are the whole trust argument in miniature: when the evidence is there it is copied, not summarized away; when it is not, the model reports the absence instead of hallucinating an incident. Both of these — not the 97.7 KB and 39 KB behind them — are what the synthesizer, and the final answer, were built from.

Identifiers survive verbatim. A subtle failure mode in any JSON round-trip is that a large integer ID — the kind used for database keys or event IDs, anything above 253 — gets silently rounded to a float or rewritten in scientific notation. The entire compaction-and-synthesis path decodes JSON in a mode that preserves exact digits (Go's UseNumber), so those identifiers survive exactly through the pre-filter, the map-reduce chunking, and the final synthesis re-parse. The distill prompt also instructs the model to copy identifiers byte-for-byte. (This covers what the LLM sees; the tool→tool template path uses standard decoding, so do not rely on it to carry a 64-bit ID between tools.)

One more piece of cleverness lives in the budget allocator. When several results share one synthesis prompt, the allocator is distillation-aware: a result that will be distilled is budgeted at its post-distill footprint (~4 KB), not its raw megabyte. Without this, one large result would grab the whole budget and starve the others; with it, the allocator knows that result is about to shrink and sizes it accordingly. And if there is no AIClient at all, distillation is simply skipped and you get the structural floor at the synthesis budgets — a safe, trimmed result, never a failure.

When one call isn't enough: map-reduce

Here is the problem the 128 KB pre-filter creates. If you pre-filter a 1 MB result down to 128 KB and then hand that to the model, you have thrown away seven-eighths of the source before the LLM ever looked at it — and the one log line that proves the incident might have been sitting at byte 500,000, in the part you discarded. Pre-filtering is fine when the result is merely large. It is dangerous when the result is huge and the finding could be anywhere in it.

So when a result's estimated token count exceeds ModelContextTokens — 150,000 tokens, which, at the framework's estimate of ~3.5 bytes per token, is about 525 KB — distillation switches to map-reduce, the classic split-into-chunks, summarize-each, then-combine pattern, run over the full result:

  1. Split the whole result into chunks of at most 128 KB, preferring structural boundaries: top-level JSON array elements first, then the elements of the dominant array inside a JSON object, then newline-delimited records, and only as a last resort a raw byte split.
  2. Map — distill each chunk concurrently (up to MapConcurrency, default 8) on the fast tier.
  3. Reduce — combine the per-chunk extracts into one final summary with a last fast-model call.

The chunker proves its value on the awkward shapes. When a result is an object wrapped around a dominant array — {"data":{"result":[…]},"status":…,"stats":…}, the shape a Loki or Prometheus response takes — it does not just chunk the array and drop the wrapper. Since a recent hardening pass, each grouped chunk replicates the wrapper and sibling fields, so the surrounding context (status, stats) reaches every chunk's model call rather than being dropped with everything outside the array. An array element too big for one chunk is handled as one or more standalone chunks — split recursively, never truncated. And when every element is oversized and split out, the wrapper still gets emitted once with a sentinel marker in place of the array — so an emptied array is never misread by the model as an authoritative "zero records."

That is not a hypothetical — it is step-28 of the sample run. The 855 KB kubectl dump cleared the ~525 KB context threshold, so the distiller chunked it into seven segments, ran all seven as concurrent fast-model calls, and reduced them into a single 3.7 KB summary with the whole result represented (source_coverage_ratio = 1.0, content_lost = false). That is eight cheap fast-model calls to read most of a megabyte — so the expensive reasoning model never had to.

The single-call caveat. Out of the box, map-reduce engages only above the ~525 KB context threshold. A result in the 128 KB–525 KB band still takes the single-call path, where Stage 1 pre-filters to 128 KB before the LLM — so the model sees the pre-filter, not the whole result. That drop is never hidden: the output carries a [partial source: the model received ~N% of the source by bytes …] note and the trim metadata records it. In the sample run, six results landed in this band and show it plainly: step-6's 389 KB result reached the model at only 33% coverage, step-14's 284 KB at 44%, and four more between 64% and 68% — each carrying the [partial source] note into synthesis. If you want the entire result in that band analyzed, there is a second, opt-in trigger — MapReduceThresholdBytes (a byte size, disabled by default) — that routes anything larger through map-reduce even when it comfortably fits the context. At the gigabyte scale, though, the answer changes: those outputs do not belong in a prompt at all — reduce them at the source, or use an extract-then-reference workflow.

What a shrunk result admits it dropped

A compaction system that quietly discards content is a liability, because the model downstream cannot tell a trimmed result from a complete one — and will happily conclude "there are no errors" when what it means is "there are no errors in the 4 KB I was shown." TruvaG3's answer is a hard rule: whenever any layer deterministically drops content, it appends a single-line note and sets an authoritative content_lost flag in the trim metadata. Every note starts with a [ so it is machine-parseable and strippable, and every note tells the downstream model the same thing — treat what is omitted as UNKNOWN, not absent.

That flag is the one signal downstream honesty keys on. Not byte ratios — re-serialization can shrink bytes with nothing lost, and escape-unwrapping can grow bytes while content was dropped — but the explicit content_lost bit, which every lossy operation is required to set. The framework even folds any specific loss flag into it defensively, so a report can never claim "verified lossless" while also flagging partial coverage. Here are the notes you can actually see in a result:

NoteEmitted byWhat it means
[trimmed: …]Structural trimWhole fields, items, or sentences were dropped to fit the budget.
[severely reduced: …]Structural trimUnder 5% of the source survived — too little to be representative.
[partial source: ~N% …]DistillationStage-1 pre-filter dropped content before the LLM (the 128–525 KB band).
[partial: N of M segments analyzed …]Map-reduceOnly N of M chunks completed — a deadline or a failed chunk call.
[findings truncated: …]Map-reduce reduceThe combined extracts were truncated to fit the budget.
[reduced without model analysis: …]Synthesis floorA byte-truncation fallback ran and no LLM analyzed the dropped tail.

There is a nice piece of discipline hiding in what is not on that list. The distiller's system prompt also asks the model to end an over-budget summary with its own [truncated: …] line — but that model-emitted form is deliberately not registered with the framework's annotation stripper. The reason: real tools emit their own [truncated: …] trailers, and if the framework stripped that pattern, it would silently delete a tool's own truncation signal, presenting visibly truncated source as complete. The authoritative, framework-guaranteed disclosure is the [partial source: …] note, not the model's best-effort one. It is the kind of distinction you only make after the alternative has caused a real problem.

Layer 3: digests, the planning path

Now the other prompt path — the one that fires during replanning. Between phases, the continuation planner re-reads the completed steps to decide what comes next. It would be wasteful to distill each one (an LLM call per step, on a path that runs every phase), and destructive to truncate them (which mangles JSON). So completed-step results are rendered as structure-complete JSON digests instead.

A digest is a skeleton of the result that is always valid JSON. An object keeps all its keys up to a 50-key cap; wider "map-shaped" objects are sampled to sorted keys plus a sentinel. Arrays are head-sampled to 3 elements plus a length sentinel. Long strings — anything over 200 characters — are shortened to a placeholder like "…(16384 chars)". A 519 KB Loki result collapses to a roughly 600-byte skeleton that still tells the planner everything it needs to know about the shape of what came back:

{
  "status": "success",
  "data": {
    "resultType": "streams",
    "streams": [
      { "stream": { "pod": "tool-abc", "level": "error" },
        "values": [
          ["1721000000000000000", "…(16384 chars)"],
          ["1721000000000000001", "…(12000 chars)"],
          ["1721000000000000002", "…(8192 chars)"],
          "…197 more of 200"
        ]
      },
      { "stream": { "pod": "tool-def", "level": "warn" },
        "values": [["1721000000000000003", "…(4096 chars)"]]
      },
      { "stream": { "pod": "tool-ghi", "level": "info" },
        "values": [["1721000000000000004", "…(2048 chars)"]]
      },
      "…197 more of 200"
    ]
  },
  "stats": {
    "ingester": { "compressedBytes": 123456 },
    "summary": { "totalLines": 400 }
  }
}

This is the addressability idea, and it is deliberate: digests are lossy on values but complete on structure. The planner never needs the 200 log streams — it needs to know they exist, and where. It writes a plan that references {{step-9.response.data.streams}}, and, per the invariant from earlier, the executor binds the entire 200-entry array from memory at run time. The planner reasoned over 600 bytes; the next step will act on the full half-megabyte.

The budget for this section is a greedy recency-fill, and it is a soft target (32 KB) that drives eviction rather than a hard cap. The rules encode what the planner most needs to see:

  • Failed steps are always kept. They carry a lot of signal in very little space — they render as short [FAILED: …] markers — so they count against the budget but are never evicted.
  • Successful steps fill newest-first until the budget is spent; older ones are evicted with a [showing N of M completed steps] note. They stay referenceable by step-ID at execution, so eviction from the prompt is not eviction from the run.
  • The newest successful step is always kept, even if it alone exceeds the budget, so the section is never empty.
  • Steps render in chronological order, so the newest sits at the end of the prompt — the position models attend to most.

Not every result is JSON, of course — logs, markdown, and CSV have no structure to digest. Those get a plain floor preview (sized by a 10,000-character cap), and a capped number of the newest non-JSON steps (default 8; set 0 to disable) may escalate to a separate continuation distiller for a fast-model summary that replaces the floor preview. This is the "rarely yes" from the table at the top: on an all-JSON workload it almost never fires, and when it does, it is fail-open — an empty summary just leaves the floor preview in place.

Cache, deadlines, and what it costs

Distillation makes real LLM calls, so it has a real cost — and the design spends carefully. The reading is done on the fast tier, several times cheaper per token than the reasoning model (roughly 3× on a Sonnet→Haiku stack, more against a frontier reasoning model). A run that distills several megabytes does the bulk of that reading cheaply and reserves the expensive model for the actual answer — in the sample run, distillation accounted for 683,956 of the 784,965 input tokens the whole request read (87%), all of it on the fast tier, while the reasoning-tier synthesis prompt was just 25,090 tokens. Map-reduce chunks run concurrently, so wall-clock time is the slowest wave plus the reduce, not the sum of all chunks. And below the threshold, nothing happens at all — a small result takes a cheap structural pass, or passes through raw if it already fits.

Two more mechanisms are worth naming, because both are strictly fail-open. The first is caching, which is opt-in: there is no cache unless you supply one (a core.DigestCache, such as one backed by Redis), so out of the box every distillation recomputes. When a cache is supplied, matching inputs — the result, the instruction, the user query, and the budget, plus a configuration salt covering the prompt version, model, target size, and routing knobs — reuse a prior distillation for a 5-minute TTL, turning scheduled and repetitive runs into cache hits. Crucially, a failed or partial output is never cached: a deadline cut, or a map-reduce run in which some chunks failed, is marked non-cacheable so a transient error cannot be served for the whole TTL. A nil or erroring cache simply recomputes — it never fails.

The second is the deadline: each compaction is bounded by a 45-second wall-clock limit, which should be set below your gateway timeout. On a timeout, the single-call path falls back to the structural floor, and the map-reduce path returns the chunks that finished plus the honest [partial: …] disclosure. The synthesis hot path is never blocked past the deadline — it degrades to a smaller, labeled result instead. This is the fail-open principle made concrete: every knob that could slow the request down has a defined, disclosed way to give up gracefully.

All of it is observable. Every distillation emits telemetry you can watch in your monitoring stack — trace events (result_distill.mapreduce_route, stage1_complete, stage2_complete, mapreduce_complete, cache_hit, llm_failed) and metrics (triggered, duration_ms, failed, mapreduce, cache_hit/miss) — and every processed step carries a result_trim record with the authoritative content_lost flag and the coverage numbers. Turn on TruvaG3's LLM-debug mode and each distill call is captured in full — prompt, response, tokens — including the individual map-reduce chunk i/N calls, shown next to the planning and synthesis calls in the registry viewer. The companion observability walkthrough[8] shows exactly what those surfaces look like on a real run.

Not to be confused with… Result compaction handles large tool and step results, the subject of this article. It sits next to — but is separate from — Conversation History Protection[7], which compacts long chat histories across turns. Different inputs, different knobs (TRUVAG3_CONVERSATION_*); the two compose without overlapping.

The whole decision, in one picture

Put the layers back together and every result a step produces runs through one decision, determined entirely by where it is going next:

result produced by a step
│
├─ used as INPUT to another tool ──────────▶ pass through RAW (fidelity-first;
│                                             cap only if MaxAgentInputBytes > 0)
│
├─ used as SOURCE for param resolution ────▶ StructuralTrimmer to 64 KB
│                                             (deterministic — never the LLM distiller)
│
├─ headed to the SYNTHESIS prompt ─────────▶ ≤ 16 KB?  structural trim to the budget
│                                             > 16 KB + AIClient?  distill (fast model)
│                                                 └─ > model context (~525 KB)?  map-reduce
│                                             no AIClient?  StructuralTrimmer floor
│
└─ headed to the CONTINUATION prompt ──────▶ valid JSON?  structure-complete digest
                                              non-JSON?  floor preview (+ rare escalation)
                                              whole section under a soft 32 KB budget
                                              (newest-first; failed + newest always kept)

Read it top to bottom, and the philosophy is visible in the branching. A tool-to-tool handoff gets the raw truth, because a program needs all of it. A resolution prompt gets a deterministic trim, because it drives its own LLM call and must not be pre-summarized. The final answer gets an LLM that reads for meaning, escalating to map-reduce only when the result is too big to read in one pass. And the planner gets a skeleton, because it is choosing the next move, not writing the answer. Four destinations, four treatments — and behind all of them, the same guarantee that the full result is still sitting in memory, untouched.

Conclusion

The uncomfortable truth about agentic systems is that the interesting results are big, and the model that has to reason over them has a small window and a shorter attention span. You cannot simply put a megabyte of kubectl output into a prompt and hope it works. You will either exceed the context window outright, or — long before that — quietly degrade the model's reasoning. TruvaG3 treats that as a first-class problem and solves it in the place it belongs — automatically, inside the orchestrator, before a single oversized result ever reaches a prompt.

What makes the solution more than a truncation hack is the shape of it. The split by destination means the planner gets structure and the synthesizer gets meaning, each exactly what it needs. The invariant that the full result never leaves memory means every summary is a safe view of the data, never a permanent deletion. The fail-open discipline means no compaction step can ever be the reason a request errors. And the honesty contract — every loss disclosed, every omission flagged UNKNOWN rather than absent — means the model downstream is never quietly misled about what it is and isn't seeing. A megabyte goes in; a few kilobytes come out — the ones that actually matter — and the request finishes cleanly. That is what result compaction is for.
