TruvaG3: An Introduction to the Microagents Framework

A guided tour of TruvaG3 — why it exists, how the architecture works in practice, what the framework ships with, and how to decide whether it fits your situation. Written for engineers and architects who already operate Kubernetes platforms.

Neelabh Tripathi · May 16, 2026

Two problems, one framework

Two things make most agent platforms difficult to run in production.

The first is architectural. Most agent frameworks ask the developer to name every tool and every peer agent in source code before the program starts. After that, the framework does not look outside that fixed list. Adding a tool means changing source code and redeploying the agent. Adding a new agent that other agents need to reach means rewriting the routing layer that decides who talks to whom. This works for a demo. It does not match how distributed systems are usually built.

The second is operational. Even when an agent framework gets the architecture right, it often brings its own runtime: its own orchestrator process, a hosted control plane, a vendor-specific workflow engine, or all three. For a platform team that already runs a working Kubernetes environment, that is not a feature — it is a new system to learn, scale, secure, and pay for. The team has to either accept a parallel operating model for agent workloads, or rebuild parts of the platform they already trust.

TruvaG3 is a Go framework that takes a different position on both counts. The architecture is the microagents reference described in a separate article — capabilities registered into a shared registry at runtime, peers addressed by logical name, orchestration inside each agent, decentralized coordination between participants. The runtime is ordinary Kubernetes: Deployments, Services, ConfigMaps, Secrets, ingress, service mesh, autoscaling, OpenTelemetry. The framework adds the agent-specific pieces — discovery, an LLM client, an orchestrator, resilience and memory primitives — and does not require anything else.

This article walks through both halves. It is meant to be read in one sitting; sections can be skipped without losing the thread.

Why TruvaG3 exists

The architectural reason

The companion article on the microagents architecture argues the case in detail, with primary-source evidence from production teams. The short version follows.

Most agent frameworks today share one wiring pattern. The developer builds an agent, gives it a list of tools, and starts a loop. If a second agent is needed, the developer either wires it into the first agent as another callable, or places both agents inside a higher-level orchestrator that decides whose turn it is. In every case, the set of participants is fixed in source code before the program runs.

Production teams report that this pattern hits real limits. Anthropic's engineering account of their multi-agent Research feature describes synchronous lead-subagent coordination as a bottleneck — the lead agent cannot steer subagents, subagents cannot coordinate, and the whole system can block on one slow subagent. Microsoft Research, writing about Magentic-One, names the static composition itself as a limitation: "Magentic-One's composition is fixed to a common set of five agents... When agents are not needed, they simply serve as a distraction to the Orchestrator... Conversely, when extra expertise might be needed, it is simply unavailable. We can easily imagine an alternative approach where agents are added or removed dynamically, based on the task need." The fix the Magentic-One authors describe — agents added or removed dynamically — is exactly the microagents approach.

The microagents architecture has five defining properties:

  • Specialized and independently deployable. Agents and tools run in their own processes, with their own release cadence and ownership.
  • Runtime registration into a shared registry. Capabilities are advertised at runtime, not wired into a caller's source code.
  • Capability-based addressing. Callers ask for a logical name, such as geocode_location; the framework resolves the name to whichever endpoint currently serves it.
  • Independently scalable, replaceable, and migratable. Callers continue to look up participants by the same name; the registry tracks where the name currently points.
  • Decentralized coordination. Each peer drives its own work. The registry mediates discovery, not control.

Two coordination layers fall out of this design. Inside each agent, a single orchestrator runs the request: it plans against the current capability catalog, executes the plan as a directed acyclic graph (DAG) with parallelism where dependencies allow, and synthesizes the response. It can return to planning when fresh data unlocks the next phase. Between participants, no such orchestrator exists. Each agent reads the registry, resolves capabilities to endpoints, and calls peers directly over HTTP. Nothing in the middle routes, sequences, or coordinates.

The result: tools and agents look the same to the LLM. A capability is a capability. Adding a new participant is purely additive — no central manifest changes, no caller code changes, no redeploys elsewhere. Within one refresh cycle of the registry, the new participant is visible to every existing caller.

One architectural property is worth surfacing here, because it underpins everything that follows: the wire protocol between agents and tools is plain HTTP/REST. Each participant exposes its capability descriptions, JSON schemas, health, and OpenAPI document over HTTP. Calls between peers are HTTP. The shared registry — Redis or Valkey by default; pluggable — sits behind the discovery interface, but everything visible to an agent, a tool, or a piece of platform tooling on the network is an HTTP/REST surface. The architecture introduces no new wire protocol for agent-tool communication — it composes well-understood distributed-systems primitives (service discovery, REST endpoints, structured contracts) into a model that fits multi-agent systems. The pattern is credible at scale not because it is new, but because every component of it has been operated in production microservice systems for years. The next subsection covers what that choice means operationally.

The operational reason

The architectural argument is necessary but not sufficient. Plenty of agent frameworks have interesting architectures and still struggle to land in enterprise environments. The reason is rarely the architecture itself; it is the operational footprint that comes with it.

Most popular agent frameworks expect one or more of the following:

  • A managed SaaS control plane that hosts the orchestration logic and stores execution state.
  • A new runtime process — a workflow engine, an agent runtime daemon, a vendor-specific scheduler — that platform teams need to deploy, monitor, scale, and upgrade separately from the rest of the system.
  • A vendor-specific data plane: a proprietary message bus, a custom storage layer, or a control plane database that does not fit into the existing observability and backup strategy.
  • A different operational model for failure handling, secrets management, deployments, and access control.

For a team that has spent years building a Kubernetes platform — Deployments, Services, Ingress, NetworkPolicies, mTLS, ConfigMaps, Secrets, HPA, an OpenTelemetry pipeline, a CI/CD path, on-call rotations — none of this is welcome. It is a parallel operating model for agent workloads. It also has real consequences: regulated and air-gapped deployments cannot use a SaaS control plane; namespace-based team isolation does not fit a single global orchestrator; on-call rotations have to learn a new failure mode set.

TruvaG3 takes the opposite position. Every agent and every tool is an ordinary HTTP service, deployed and operated the way any other workload in the cluster is deployed and operated. Specifically:

  • Agents and tools are Deployments behind Services. The framework registers the Kubernetes Service DNS name, not pod IPs. The cluster's own Service load-balances calls across replicas. Horizontal Pod Autoscaler scales them like any other workload.
  • Configuration is through environment variables and ConfigMaps. Secrets are managed through Kubernetes Secrets.
  • Observability is native OpenTelemetry. Traces and metrics flow to the existing OTLP-compatible backend — Prometheus, Jaeger, Grafana, Loki, Tempo, or a commercial equivalent. No adapters.
  • The default registry is Redis or Valkey. Most teams already operate one or both. The interface is pluggable, so etcd, Consul, or a custom backend can replace it.
  • There is no required SaaS control plane. Self-hosted is the default. Air-gapped operation is supported, via namespaces.

One of these choices is worth pulling out, because it changes the operational story for the whole framework.

The component-facing interface is HTTP/REST. Runtime calls between agents and tools are HTTP. Each component exposes its capability contract over HTTP at standard paths: the catalog at /api/capabilities, the individual capability endpoints at /api/capabilities/{name}, the auto-generated JSON Schema at /api/capabilities/{name}/schema, and the full OpenAPI document at /openapi.json. Health checks are HTTP. Telemetry export is OTLP over HTTP. There is no proprietary wire format and no sidecar to inject. Agents look up peers through the shared registry (Redis or Valkey by default; pluggable), but everything visible on the network between participants — runtime, contract, observability — is the same REST surface that any well-built microservice in your cluster already presents.

This is a structural property, not a compatibility claim. Because the protocol is the one your platform team already operates, every piece of infrastructure that already works on your REST services works on TruvaG3 components in the same way: API gateways (Kong, Ambassador, Nginx), service meshes (Istio, Linkerd), ingress controllers, network policies, identity providers, mTLS, OAuth and JWT validation, RBAC, audit logging, rate limiters, web application firewalls, monitoring, API governance tools, OpenAPI consumers (Swagger UI, Postman, code generators). Nothing has to be re-built or re-secured for agent workloads. Security and authentication and authorization patterns the team has already standardized on apply by default, because the thing being secured is just an HTTP service.

The combined claim is straightforward. TruvaG3 is architecturally different from most agent frameworks, because it inherits the microagents pattern. It is also operationally familiar, because the platform layer is the same Kubernetes platform the team is already running — and because the wire protocol is the same HTTP/REST contract every other service in the cluster already follows. Most frameworks pick one or the other; TruvaG3 is shaped around the assumption that both matter.

How the architecture works, briefly

This section is a compressed restatement of the architecture, enough to follow the rest of the article. For the full treatment — including production-team citations, the wiring problem in detail, and two captured execution traces from a running cluster — see the architecture article.

The architecture is built around a single primitive: a capability registry. Every participant publishes the capabilities it offers into a shared index, each identified by a logical name. These names are runtime facts about the deployment; they are not configuration carried in any caller's code, and no participant references a peer's capability by name in its own source. When a request needs to be planned, the framework hands the registry's current contents to the LLM as the planning catalog. The LLM picks capabilities; the framework dispatches each chosen step to the address the registry currently lists for that name.

A registration carries more than a name. It also carries:

  • The network address (a Kubernetes Service DNS name, in cluster deployments) and the endpoint path.
  • A natural-language description, so the LLM can decide whether a capability is relevant to a request.
  • Structured field hints for inputs and outputs: name, type, example value, short description. These hints let the LLM generate correct JSON and let the framework validate it.
  • An optional full JSON Schema for deployments that want stricter validation.

Registrations are kept alive by heartbeats. Each participant refreshes its entry every 15 seconds against a 30-second TTL. If a participant crashes or loses network connectivity, its entry expires within one TTL window. Liveness is the registration — there is no separate health-check system to keep in sync.

Three roles run on top of the registry:

RoleRegisters capabilities?Discovers peers?Has internal orchestrator?
ToolYesNoNo — passive HTTP endpoint
AgentYesYesYes — runs a plan-execute-synthesize loop
Registry——No — passive index

The difference between tools and agents matters, and TruvaG3 enforces it at compile time. A Registry interface lets a component register but not discover. A Discovery interface extends Registry with the lookup methods. Tools satisfy Registry only. Agents satisfy Discovery. A tool cannot call discovery methods, because those methods do not exist on its interface. The check happens before the code runs:

// Tools can only register themselves (passive components)
type Registry interface {
    Register(ctx context.Context, info *ServiceInfo) error
    UpdateHealth(ctx context.Context, id string, status HealthStatus) error
    Unregister(ctx context.Context, id string) error
    // No discovery methods — tools cannot find other components
}

// Agents can both register and discover (active orchestrators)
type Discovery interface {
    Registry  // Embeds registration capability
    Discover(ctx context.Context, filter DiscoveryFilter) ([]*ServiceInfo, error)
    FindService(ctx context.Context, serviceName string) ([]*ServiceInfo, error)
    FindByCapability(ctx context.Context, capability string) ([]*ServiceInfo, error)
}

In most frameworks the tool/agent boundary is a convention. In TruvaG3 it is a property the type system checks.

Naming note. A TruvaG3 Tool is not the same as an MCP (Model Context Protocol) tool. A TruvaG3 Tool is an independent microservice running in its own container, exposing one or more capabilities over HTTP. An MCP tool is a single named function inside an MCP server. The cleaner mapping is: a TruvaG3 Tool plays the role of an MCP server, and a TruvaG3 capability plays the role of an MCP tool.

What TruvaG3 ships with

The framework is intentionally modular. The core module is the only required dependency; everything else is opt-in. Six modules ship in the box:

  • core — defines the framework's interfaces (Component, Registry, Discovery, AIClient, Telemetry), base implementations for tools and agents, configuration loading, the pluggable service registry, and the auto-generated HTTP surface (capability endpoints, /health, /openapi.json). Every component depends on it.
  • ai — provider-neutral LLM client with zero-configuration provider detection, provider and model aliases, chain-client failover, and embeddings. Add it when an agent needs to call an LLM.
  • orchestration — the per-agent reasoning loop: dynamic LLM-driven planning, DAG execution with parallelism, iterative multi-phase plans, streaming, human-in-the-loop approvals, async tasks, and scheduled execution. Add it when an agent coordinates multi-step work.
  • memory — shared agent memory (episodic events, knowledge store, semantic recall) and per-user memory (extraction, reconciliation, forget). Add it when agents need state across requests.
  • resilience — circuit breakers, retry with exponential backoff and jitter, panic recovery. Add it for robust fault isolation between components.
  • telemetry — OpenTelemetry-native metrics, traces, and structured logging. Cross-cutting; the other modules wire it in through dependency injection.

The walk below is a tour through what each of these modules provides, not a manual — each subsection has a link to the corresponding section of the Framework Features Guide for the details that matter at implementation time.

1. Component runtime

Behind every TruvaG3 component — tool or agent — is a small runtime that handles the work of being a service: starting an HTTP server, wiring panic-recovery and logging middleware, registering capabilities with the discovery layer, propagating loggers and telemetry into handlers, refreshing heartbeats, and providing a bounded HTTP shutdown the application can invoke on a termination signal. The developer writes the business logic — the API client, the domain handlers — and the framework supplies everything else.

Functional-options API, predictable defaults. A component starts life with core.NewFramework(component, opts...). Every operational property is set through a With... option — explicit when you need to override, invisible when defaults are fine. The options that come up in practice:

  • WithName — the logical name the framework registers in discovery and uses in logs, metrics, and traces.
  • WithPort — the HTTP port to listen on. Standard Kubernetes deployments leave this at the container port (e.g., 8080).
  • WithNamespace — a logical grouping label (e.g., "production", "staging") that is attached to the component's registry metadata and emitted in logs and traces. It is not a Kubernetes namespace, and it does not key-partition the registry — the Redis registry key namespace is currently hardcoded to truvag3.
  • WithRedisURL / WithDiscovery — turn on the registry connection. Pluggable backends sit behind these.
  • WithCORS / WithCORSDefaults — opt in to CORS for browser-facing components. Off by default, since most internal services do not need it.
  • WithMiddleware — wire arbitrary HTTP middleware into the handler chain. Panic recovery, request/response logging, and (when enabled) CORS are wired automatically by the framework. Distributed tracing is NOT auto-wired — application code adds it through this option, typically with telemetry.TracingMiddleware or TracingMiddlewareWithConfig. This is also the hook for application-specific middleware (auth, rate-limiting, audit).
  • WithOpenAPI — opt in to the auto-generated OpenAPI document at /openapi.json. Off by default for security; see §3 for what the document contains and §12 for when to enable it.
  • WithDevelopmentMode — pretty (human-readable) logs, debug log level, text log format. Off in production deployments. (Validation relaxation for AI/discovery is separate, via WithMockAI / WithMockDiscovery.)

Most operational options have a corresponding environment variable (TRUVAG3_*) so the same binary can run in many environments without recompilation. Options that take function values — middleware, custom loggers — are code-only. The precedence order is documented and predictable: explicit code overrides take priority, environment variables come next, framework defaults are the fallback.

Standard endpoints, no boilerplate. The framework auto-mounts a small set of endpoints on every component. Hit any running tool or agent and these are always there:

  • GET /health — liveness probe. The default tool handler returns {"id":..., "name":..., "status":"healthy", "type":"tool"} — e.g. weather-tool-v2 returns {"id":"weather-tool-v2","name":"weather-tool-v2","status":"healthy","type":"tool"}. The default agent handler returns a smaller shape: {"status":"healthy", "agent":..., "id":...} (no type; the name field is keyed agent). Bundled chat agents typically override /health with a richer handler that includes orchestrator status. The path is configurable; the default /health works with Kubernetes liveness and readiness probes without any extra configuration.
  • GET /api/capabilities — the component's capability catalog. See §3.
  • POST /api/capabilities/{name} — the auto-generated endpoint per capability. Components do not have to write HTTP handlers; the framework binds the capability handler function to this path automatically when the capability is registered without an explicit endpoint.
  • GET /api/capabilities/{name}/schema — auto-generated JSON Schema per capability. Mounted only when the capability declares an InputSummary (Phase 2 of the schema model — see §3).
  • GET /openapi.json — full OpenAPI document (when enabled).

Agents that need to expose the live registry snapshot register a GET /discover capability themselves — the bundled chat agents do this. It is a convention, not a framework-mounted endpoint. See §2 for the discovery story.

Lifecycle. The framework manages the component's lifespan in this order:

  1. Setup — configuration loading, dependency injection (registry, telemetry, memory store for agents), middleware chain wiring.
  2. Initialize — the component registers itself with the discovery registry and starts its heartbeat goroutine. Tools also re-register with the resolved address when the HTTP server actually binds; agents log the address but rely on the Initialize-time registration.
  3. Background runnables start — anything registered via RegisterRunnable (memory sweepers, scheduled-executor workers, custom periodic jobs) starts in parallel goroutines that receive the same context.
  4. HTTP server starts — the component begins serving requests on a blocking ListenAndServe call.
  5. Shutdown — BaseAgent.Stop and BaseTool.Shutdown call http.Server.Shutdown (bounded by HTTP.ShutdownTimeout, code default 10s), deregister from discovery, and stop background runnables cleanly. Two important caveats for the current code: (a) Framework.Run(ctx) does not itself watch ctx to invoke shutdown — applications wire SIGTERM/SIGINT in main and the bundled examples typically end the process with os.Exit after cancellation, so framework-managed graceful shutdown only happens when application code explicitly calls Stop/Shutdown; (b) TRUVAG3_HTTP_SHUTDOWN_TIMEOUT is declared on the struct as a tag but is not currently loaded by LoadFromEnv() — change the value via code (Config.HTTP.ShutdownTimeout) for now.

The 10-second code default for the shutdown timeout sits comfortably inside Kubernetes' default terminationGracePeriodSeconds of 30s, leaving headroom to drain in-flight requests before the kubelet sends SIGKILL.

Dependency injection by default. The framework wires dependencies into the component struct so handlers reach them without globals. The injected set differs by component type: tools get a Registry (registration only, no discovery), Logger, Telemetry, and an optional AIClient — tools deliberately have no Memory field, since response caching is a tool-local concern with tool-specific TTL/eviction semantics. Agents get a full Discovery (registration + lookup), Logger, Telemetry, Memory, and an optional AIClient. Tests substitute mocks for any of these through the standard interfaces; the in-memory implementations (core.NewMockDiscovery, core.NewMemoryStore) ship with the framework specifically for tests.

Background runnables. Long-running work that needs its own goroutine — a memory eviction sweeper, a metric reporter, a periodic refresh job — registers through RegisterRunnable. The framework starts it before the HTTP server, supplies a cancellation context, and stops it during graceful shutdown. The bundled scheduled-executor is built on this pattern; so are custom jobs application teams write for their own deployments.

Working examples in the cluster. Every tool and agent in the bundled examples uses this runtime — from compact single-capability tools to the full chat agents. The weather-tool-v2 and country-info-tool examples show what a focused tool looks like in practice. The my-tool directory is a coding-agent scaffold (with PROMPT.md) for bootstrapping a new tool from scratch, not a runnable example. The travel-chat-agent shows what the same runtime looks like when an agent uses the full feature set — discovery, AI client, memory hooks, HITL, streaming.

2. Runtime discovery

Discovery is the primitive that makes the whole microagents architecture possible: agents find tools and other agents by what they can do, not by hardcoded addresses. A capability registered by one component becomes visible to every other component on the next read. Add a new tool, and every existing agent sees it within seconds — no agent code change, no redeploy. Remove a tool, and it disappears within seconds too.

A single registry holds tools and agents on equal footing — any number of either — each publishing one or more capabilities that any other component can look up by name. All of it sits behind one Go interface called core.Discovery. Capability lookups are key-value reads, so the registry scales with the number of distinct capability names in the deployment, not with the wiring complexity between components.

Pluggable backend. Redis (or Valkey, which speaks the same protocol) is the default registry — they are key-value stores most platforms already operate for sessions, caching, or queuing. The framework ships two implementations of core.Discovery: the Redis backend for production and an in-memory mock for tests. Other systems (etcd, Consul, a custom backend) can be plugged in by satisfying the core.Discovery contract — the adapter is yours to write. Switching backends is a deployment configuration change, not an application code change.

Three lookup methods, each for a different question.

  • FindByCapability(ctx, "geocode_location") — "give me every component that can do this." The workhorse. The orchestrator uses this when the LLM has chosen a capability and the framework needs the address that currently serves it. Most calls in a running system go through this path.
  • FindService(ctx, "weather-tool-v2") — "give me this specific component, regardless of what it does." Useful for health checks, admin operations, or any case where the caller already knows the participant by name.
  • Discover(ctx, filter) — "give me everything that matches these criteria." The filter combines component type (tool vs agent), name, capability list, and metadata — useful for cross-cutting queries like "list all agents that expose a streaming capability." The Redis key namespace used by a Discovery client is set when the client is constructed (default truvag3 through the auto-wired path; override by injecting a client built with NewRedisDiscoveryWithNamespace) and applies to every query made through it.

TTL-backed leases, not separate health checks. Every registration carries a 30-second TTL. Each component refreshes its entry every 15 seconds (half the TTL, with jitter to spread load). If a component crashes, loses network, or simply stops responding, its entry expires within one TTL window — no separate liveness probe required, no orphan entries to clean up. The gauge discovery.last_health_check_timestamp exposes the Unix timestamp of each component's last heartbeat per registry, so a stale value is the canonical signal that something is wrong.

Kubernetes Service DNS by default — replicas just work. In a Kubernetes deployment, the framework registers the Kubernetes Service DNS name (for example, weather-tool-v2-service.truvag3-examples.svc.cluster.local), not individual pod IPs. A discovered call therefore goes through the cluster's own Service, which load-balances across all healthy pods that match the selector. The practical consequence:

  • Horizontal Pod Autoscaler can scale a tool from 1 to 50 replicas without changing a single registry entry.
  • Rolling updates, pod restarts, and node failures are handled by Kubernetes; discovery does not even notice.
  • Outside Kubernetes (bare-metal, Docker Compose), the framework falls back to pod-scoped addresses — same registry shape, different default for what gets registered.

Service mesh compatibility. Because the framework advertises the Service DNS name and nothing else, transparent service meshes like Istio and Linkerd work without any special configuration. The mesh handles mTLS, traffic policy, retries, circuit breaking, and mesh telemetry at the network layer; the framework handles capability discovery at the application layer. The two are orthogonal — neither needs to know the other exists.

Live metrics, end-to-end. The framework emits these under the OTEL meter truvag3-telemetry; the names below are the canonical OTEL names (Prometheus exporters typically render them as truvag3_discovery_registrations_total and so on — the exact suffix depends on your exporter configuration).

  • discovery.registrations / discovery.unregistrations — components joining and leaving the registry. A spike in registrations on a deployment is expected; a spike at any other time is investigation-worthy.
  • discovery.lookups + discovery.lookup.duration_ms — read traffic against the registry, with latency. Tells you whether the registry itself is healthy under load.
  • discovery.services.found — gauge tracking how many results each lookup returned. A drop to zero means a capability is currently unavailable; a sudden jump may indicate duplicate registrations.
  • discovery.health_checks + discovery.health_check.duration_ms — heartbeat traffic and how long the registry takes to acknowledge each refresh.

All of these metrics are emitted in the OTLP standard, so they flow into any OpenTelemetry-compatible backend your team already operates — Prometheus + Grafana, Datadog, Honeycomb, New Relic, Grafana Cloud, or any equivalent. No framework-specific monitoring tooling needs to be introduced for agent workloads.

Inspect the live registry. The bundled chat agents register a GET /discover capability that returns the full registry snapshot from that component's point of view (agents and tools, each with their capabilities and addresses) — see travel-chat-agent, devops-chat-agent, and research-agent. The Registry Viewer web app reads the same data and renders it as a browsable dashboard. Both are useful during development and incident response — they answer the basic question "what does my system currently look like?" without reading any logs. Tools and other agents can register the same capability when they want to expose it; the underlying lookup is just a call into core.Discovery.

3. Self-describing capability contracts

How does an agent know what JSON to send a tool? In most frameworks, the agent's source code holds a hand-written wrapper for each tool — signature, field names, types — which has to stay in sync with the tool's actual API. When the tool changes, the wrapper drifts. When wrappers drift, the agent stops working in subtle ways that are hard to debug. TruvaG3 takes a different approach: the contract is part of the registration, not part of the caller. Every capability publishes everything an LLM needs to generate a valid payload, everything the framework needs to validate it before sending, and everything a developer needs to inspect it from a browser — all from the same source of truth.

Three layers, each more precise than the last. A registered capability carries:

  1. Natural-language description — what the capability does, what inputs it expects, what outputs it returns. The LLM reads this when deciding whether the capability is relevant to a request at all. Research on JSON-schema-aware LLM generation suggests good descriptions land roughly 85-90% accuracy on payload generation by themselves.
  2. Structured field hints — for each input and output field: name, type (string, number, boolean, object, array), example value, and short description. Precise enough that the LLM knows the input field is called location and not city, that amount should be a number, and that the response will contain currency.code. Field hints typically lift payload accuracy to ~95%.
  3. JSON Schema (optional) — for deployments that need strict validation, the framework auto-generates a JSON Schema draft-07 document from the field hints, served at /api/capabilities/{name}/schema. The orchestrator can fetch this schema and validate the LLM-generated payload before sending the request, catching the remaining edge cases — wrong types, missing required fields, values outside the allowed set.

The layers stack. Phase 1 ships by default for every registered capability. Phase 2 is the recommended baseline for any production tool. Phase 3 is opt-in for the small set of cases where validation has to be perfect.

Everything is reachable over HTTP. The same self-describing data that the framework uses internally is reachable by anyone on the network through standard REST endpoints — auto-generated, no extra code:

  • GET /api/capabilities — the component's full capability catalog, including descriptions, input and output field hints, endpoint paths, and input/output content types.
  • POST /api/capabilities/{name} — the capability endpoint itself (the handler that runs the work). The framework decodes the JSON request body and invokes the registered handler.
  • GET /api/capabilities/{name}/schema — the auto-generated JSON Schema (draft-07) for that capability's input. Mounted only when the capability declares an InputSummary. Useful for code generators, validators, and contract tests.
  • GET /openapi.json — a complete OpenAPI document covering every capability the component exposes, with both Input and Output schemas registered as named components. Drops straight into Swagger UI, Postman, code generators, and API gateways that consume OpenAPI.

The practical consequence: the people, scripts, and platforms that already integrate with REST services in your organization can integrate with TruvaG3 tools the same way. There is no separate API documentation site that has to be kept in sync with the code, no client SDK with hardcoded signatures, no version-pinned schema file checked into a wiki — the registration is the documentation.

Output schemas catch a class of LLM mistakes. Most planning systems only describe inputs; output structure is left implicit. TruvaG3 also publishes an OutputSummary for every capability. When a multi-step plan references upstream output — {{step-1.response.data.products}} — the orchestrator validates that products is actually a declared field in step 1's output. If the LLM hallucinated a field that does not exist, the validation rejects the plan before any step runs and asks for a corrected plan. Field-level hallucination becomes a recoverable retry instead of a confusing runtime error.

Schema cache for high-traffic deployments. When strict validation is enabled, the orchestrator caches fetched schemas in Redis (the default backend) with a 24-hour TTL — shared across all agent replicas, so even with horizontal scaling each schema fetch happens at most once per TTL window. The cache exposes hit-rate statistics through standard metrics; configurable TTL and key prefix for multi-tenant deployments.

Working examples in the cluster. Every bundled tool ships with all three layers wired. The weather-tool-v2 example, for instance, publishes get_current_weather with a natural-language description, field hints declaring lat and lon as required numbers with realistic example values, an auto-generated JSON Schema reachable at /api/capabilities/get_current_weather/schema, and the capability appearing in the tool's /openapi.json with separate Input and Output schema components.

4. Observability

The depth of telemetry is one of the framework's most distinctive properties. Every meaningful operation across every layer of the stack emits a span and one or more metrics — not just at the agent boundary, but inside the orchestrator, the AI client, the discovery layer, the memory subsystem, the pipeline hooks, and the prompt builder. A single user request that crosses three services typically produces 40+ spans across roughly 28 distinct operation types, with rich attributes on each.

Distributed traces. W3C TraceContext propagation reassembles a request that spans several agents and tools into one trace in any OTLP-compatible backend (Jaeger, Tempo, Honeycomb, Datadog, etc.). Each span carries operation-specific attributes:

  • AI calls — provider, model, prompt and completion token counts, total tokens, cost in USD, finish reason, streaming flag, retry attempt, max retries, chain provider index, attempt status.
  • Orchestrator phases and steps — plan ID, phase number, total phases, steps per phase, terminal flag, termination reason; per step: agent name, capability invoked, attempt count, success status, duration.
  • Synthesis — model, provider, prompt/completion/total tokens, step count, success and failure counts, finish reason, streaming flag.
  • Pipeline hooks — hook name and stage (before-planning, after-planning, after-execution, after-synthesis), duration, short-circuit outcome.
  • Memory operations — recall path (identity, query, stable namespace, summary, universal), candidate count, neighbors found, facts recalled, search duration.
  • Prompt building — builder type, prompt size, request size, capability info size, type-rule count, custom-persona flag.

Metrics. 240+ base metric families exported via OTLP/HTTP to any OpenTelemetry-compatible backend, with cardinality-protected labels. Coverage spans every framework layer:

  • Orchestration — plans generated, plan success rate, average phases per request, plan-generation duration, continuation re-plan rate, parse-error counts.
  • AI — requests per provider and model, token usage, request duration, failure counts, chain failover and exhaustion events, embedding requests, embedding tokens.
  • Discovery — lookups, registrations, deregistrations, health-check duration, services found per lookup.
  • Memory — cache hits and misses, eviction rate, ops rate, conversation-history compaction duration, episodic events recorded.
  • HITL — checkpoints created, decisions per outcome (approved, rejected, edited, expired).
  • HTTP — request and response sizes, durations, status codes — at both client and server.

Structured logging. JSON logs carry trace IDs from request context, so logs and traces correlate in Loki and Jaeger without any extra wiring.

5. Vendor-agnostic AI provider layer

The ai module sits behind a single Go interface — core.AIClient — that every agent talks to. Behind that interface, the framework supports eleven providers out of the box and lets teams plug in their own. Application code never names a provider in source; it asks for a client and gets one wired to whichever provider the deployment has configured. The same agent image runs against OpenAI in one environment, a self-hosted Ollama model in another, and an Anthropic-with-Groq-fallback chain in a third — without recompiling.

Eleven providers ship in the box. Four native (each with first-class support for that provider's API features) and seven OpenAI-compatible (any service that exposes an OpenAI-compatible HTTP API):

  • Native: openai, anthropic, gemini, bedrock
  • OpenAI-compatible: openai.groq, openai.deepseek, openai.xai, openai.mistral, openai.qwen, openai.together, openai.ollama

Provider names are logical; they map to concrete endpoints at runtime through environment variables. Switching a deployment from openai to openai.groq is one env-var change — no code change, no rebuild.

Zero-configuration provider detection. ai.NewClient() scans environment variables, detects which API key is present (OPENAI_API_KEY, ANTHROPIC_API_KEY, GEMINI_API_KEY, …), picks the highest-priority configured provider, and returns a ready-to-use client. Two metrics expose what happened (canonical OTEL names; Prometheus exporters add _total and replace dots with underscores):

  • ai.provider.detection — counter of detection runs.
  • ai.provider.selected — counter labeled by which provider won, so dashboards can show provider mix across environments at a glance.

Six portable model aliases. Instead of hardcoding model IDs like gpt-4.1-mini or claude-sonnet-4-5-20250929, application code requests a role. Each provider has its own mapping:

  • default — provider-recommended workhorse (OpenAI → gpt-4.1-mini, Anthropic → claude-sonnet-4-5, Gemini → gemini-2.5-flash)
  • fast — cheapest / lowest-latency option
  • smart — best-reasoning model (OpenAI → o3, Anthropic → sonnet-4-5, Gemini → gemini-2.5-pro)
  • premium — maximum-intelligence model (Anthropic → opus-4-5, Gemini → gemini-3-pro-preview)
  • code — best for code generation
  • vision — supports multimodal image input

Each alias can be overridden per environment with TRUVAG3_{PROVIDER}_MODEL_{ALIAS} env vars — so you can pin a specific model in production while letting development float to the latest.

Chain client with automatic failover. A chain client wraps multiple providers and tries them in order; if a request gets a retryable error (rate limit, 5xx, transient failure), it fails over to the next provider transparently. The chain is instrumented at every level:

  • ai.chain.attempt — every provider attempt, labeled by provider and attempt index.
  • ai.chain.failover — counter of failover events. A rising rate is the canonical signal that the primary provider is degraded.
  • ai.chain.exhausted — counter of requests where every provider in the chain failed. Should be near zero in healthy operation.
  • ai.chain.stream.success / ai.chain.stream.partial / ai.chain.stream.failure — outcomes for streaming requests, which can succeed, partially succeed (some tokens before failure), or fail.

The trace view of a failover looks like this: a parent ai.chain.generate_response span containing one or more ai.chain.provider_attempt spans, each carrying ai.chain.provider, ai.chain.provider_alias, ai.chain.provider_index, ai.chain.attempt_status, and ai.chain.attempt_duration_ms. The reason a request took two seconds is visible without reading logs.

Per-request cost annotation. Every ai.generate_response and ai.stream_response span carries an ai.cost_usd attribute computed from prompt and completion token counts at the model's list price. The pricing table covers about 20 model families (current OpenAI, Anthropic, Gemini, Groq's gpt-oss) and is treated as an estimate rather than a billing source of truth. The point is per-trace cost visibility in Jaeger or any tracing backend — clicking on a slow trace also tells you what that request cost.

Standard AI metrics across all providers.

  • ai.request.total + ai.request.duration_ms + ai.request.failures — request rate, latency, and error rate per provider/model.
  • ai.tokens.used — token throughput, labeled by provider, model, and token type (prompt vs completion).
  • ai.embedding.duration_ms, ai.embedding.tokens_total, ai.embedding.success, ai.embedding.errors — separate instrumentation for embeddings, which most agent frameworks bundle into the same metric as generation.

Custom providers. Internal gateways, private endpoints, or new external services all plug in behind the same AIClient interface. The provider registry is what auto-detection consults, so a custom provider becomes a first-class option once registered. The histogram ai.provider.detection.duration_ms tracks how long detection itself takes, which becomes useful when a registry has many providers.

6. Orchestration

The orchestrator is what turns a list of capabilities and a natural-language request into an answer. It is the per-agent reasoning loop, and it is built around dynamic LLM-driven planning — the part of the framework that most directly uses the microagents architecture. No hand-written routing graphs, no pre-wired tool list in source code: the plan is generated against whatever is in the registry at the moment the request arrives.

The plan-execute-synthesize loop. A request enters the orchestrator. The orchestrator hands the live capability catalog to the LLM and asks for a plan. The LLM returns a directed acyclic graph (DAG) of steps — each step names a capability and lists the steps it depends on. The executor then runs the DAG: independent steps in parallel, dependent steps in topological order. When all steps finish, a synthesis call composes the response. Every operation along this path is instrumented, with one span per layer:

  • orchestrator.process_request_streaming — the top-level span. Attributes: iterative_planning, phase_count.
  • orchestrator.phase.N — one per planning phase. Attributes: phase_number, plan_id, plan_source, steps_in_phase.
  • orchestrator.step.step-N — one per step. Attributes: step.agent_name, step.capability, step.attempts, step.duration_ms, step.success, step.namespace.
  • orchestrator.synthesis — the final composition call. 14 attributes: model, provider, prompt and completion tokens, total tokens, prompt and response length, finish reason, streaming flag, step count, success and failure step counts, chunks sent, duration.

Iterative multi-phase planning. When the LLM cannot plan the full response upfront — because the destinations come from a search, or the coordinates come from geocoding, or the next step depends on what the previous step returned — the orchestrator returns to planning after a phase completes and feeds fresh results back as planning context. Plans are capped at 5 phases by default (MaxPhases) with a 200-step total budget (MaxTotalSteps) and a 180-second per-phase timeout (PhaseTimeout), tunable through environment variables. The Switzerland trip example in the architecture article shows this in practice: phase 1 calls one web search, phase 2 fans out three parallel geocoding calls, phase 3 fans out six parallel weather and hotel calls — 10 tool invocations in three phases, 6-way parallelism at peak, 29 seconds wall time. The metric orchestration.phases_per_request exposes the actual phase count distribution so a production team can see whether their workload is mostly single-phase, multi-phase, or both.

Plan validation, before any step runs. The LLM occasionally produces plans that are structurally invalid — references to dependencies that do not exist, references to steps in earlier phases that were never created, references to plan macros that are not registered. The orchestrator catches each of these classes before execution starts and emits a counter per rejection class:

  • orchestration.plan.rejected_missing_dependency
  • orchestration.plan.rejected_cross_phase_missing_step
  • orchestration.plan.rejected_unknown_macro

A rising rejection count is the canonical signal that the planning prompt has drifted, the LLM provider has been swapped to a less capable model, or a new tool's schema has confused the planner — visible without reading a single log line.

Tiered capability selection (large-catalog mode). Once a deployment grows past 20 registered capabilities (the default TRUVAG3_TIERED_MIN_TOOLS threshold), sending all schemas to every planning call wastes tokens and can exceed the context window. Instead, the orchestrator sends lightweight tool summaries to the planner first, asks for the tool selection, then fetches full schemas only for the chosen tools. The selection step is capped at 2000 tokens by default (TRUVAG3_TIERED_SELECTION_MAX_TOKENS). This is enabled by default and configurable per deployment.

Per-step retry, with semantic re-resolution. Each step gets an initial attempt plus two retries by default (overridable via TRUVAG3_STEP_RETRY_MAX_ATTEMPTS). Generic retry with exponential backoff handles transient transport errors. For input-level failures — wrong field name, missing required value, ambiguous parameter — the orchestrator goes further: it can ask the LLM to read the error, the original payload, and the capability's input schema, then propose corrected parameters before the next attempt. The counters orchestration.error_analysis.retry and orchestration.error_analysis.no_retry track whether the LLM judged the error recoverable; orchestration.error_analyzer.llm_latency_ms tracks how long the analysis itself took.

Result trimming for large step outputs. Tool responses sometimes weigh in at tens of kilobytes — a clinical record, a full Confluence page, a deep telemetry payload. Pushing these raw into the next planning prompt would waste tokens and confuse the LLM. The orchestrator trims them before they enter the next prompt: structural trimming first (preserves JSON shape, key names, representative samples), with an optional LLM-summarization (distill) pass for very large outputs. Tracked by orchestration.result_trim.triggered and orchestration.result_distill.triggered; the original byte size is recorded in orchestration.result.original_size_bytes, which makes it easy to identify which tools are producing oversized responses.

Streaming and clarification. The orchestrator can emit progress events while work is running — phase started, step completed, synthesis token chunks — suitable for chat UIs and long-running operations. When the planner needs information it cannot infer (a date, a destination, an account ID), it surfaces a structured Clarification request rather than hallucinating a value. Simple chat UIs forward the natural-language response; richer UIs can render structured prompts from the clarification field.

7. Reliability and error recovery

Failure is a normal part of running distributed systems. Networks degrade, external APIs rate-limit, downstream services go through deployments, and LLMs sometimes pass slightly wrong arguments. A framework that ignores this turns every transient problem into a user-facing error. TruvaG3 builds error handling into the request path as a layered, instrumented system — so most failures are absorbed and recovered from before they ever reach the user. The orchestrator-internal recovery layers (semantic re-resolution, LLM error analysis, result trimming) are covered in §6 above; this section is about the foundation underneath them: how tools report errors and the resilience primitives the framework provides.

Structured tool errors, not opaque strings. Every tool that returns an error returns a typed ToolError with a Category field. There are five categories, and each one tells the orchestrator something specific about what to do next:

  • INPUT_ERROR — the request was malformed (wrong field name, wrong type, value out of range). The orchestrator can route this to the LLM error analyzer, which will read the error and propose corrected parameters before the next attempt.
  • NOT_FOUND — the requested resource does not exist. Usually non-retryable; the orchestrator surfaces it to the synthesis step so the response can tell the user the resource is missing.
  • RATE_LIMIT — the upstream API quota was exceeded. Retryable with backoff; the framework waits and tries again.
  • AUTH_ERROR — credentials are invalid or missing. Non-retryable on its own (no point in retrying the same bad token); escalates to operator attention.
  • SERVICE_ERROR — the upstream service is temporarily unhealthy (5xx, network error). Retryable with backoff.

Because the category is explicit, the orchestrator's response is deterministic rather than guessed from the error message text. A tool that returns RATE_LIMIT gets retried with backoff; a tool that returns AUTH_ERROR does not.

Step retry with exponential backoff and jitter. Each step in a plan gets an initial attempt plus two retries by default (TRUVAG3_STEP_RETRY_MAX_ATTEMPTS, total 3). The wait between attempts grows exponentially — 100ms initial, doubling each attempt, capped at 5 seconds — with ±10% jitter added so that a fleet of agents retrying against the same backend does not synchronize into a thundering-herd retry storm. These defaults come from the resilience module's DefaultRetryConfig; every value is configurable per call.

Circuit breakers for failure isolation. A single misbehaving tool can affect every agent that calls it. TruvaG3 ships a circuit breaker primitive (resilience.CircuitBreaker) that any agent can wrap around outbound calls. Three states:

  • Closed — normal operation; calls flow through.
  • Open — too many failures in the recent window; calls fail fast without touching the upstream service, giving it time to recover.
  • Half-open — after a recovery timeout, a limited number of calls is allowed through to test whether the downstream is healthy again. Success closes the breaker; failure reopens it.

Thresholds are configurable: error rate (default 0.5, meaning open if more than half of recent requests fail), volume threshold (minimum request count before evaluation), and recovery timeout. The breaker's state, transitions, and outcomes are all instrumented:

  • agent.circuit_breaker.success / agent.circuit_breaker.failure — outcomes of attempted calls.
  • agent.circuit_breaker.rejected — calls fast-failed by an open breaker. Tells you how much load the breaker absorbed.
  • circuit_breaker.state_change — counter of state transitions, labeled from and to; filtering by to=open tells you how often a downstream tripped the breaker.
  • circuit_breaker.current_state — gauge of the current state (closed / open / half-open), per breaker.
  • circuit_breaker.duration_ms — histogram of call durations recorded through the breaker.

An operator looking at a Grafana panel for circuit breakers can see immediately which downstream services are degraded — without reading any application logs.

Panic recovery, so a single bad request does not crash the process. Go's panic mechanism is occasionally triggered by unexpected conditions — a nil dereference inside a third-party library, a malformed response, a corrupt payload. The framework wraps execution paths with recover(), so a panic during one request is caught, logged with full stack trace, and converted into a structured error returned to the caller. The agent process keeps serving other requests. Without this, one buggy code path could take down an entire pod and trigger a cascade of restarts.

How the pieces fit together. A typical failure scenario, end to end:

  1. An agent makes an outbound call through a circuit breaker. The breaker is closed; the call goes through.
  2. The downstream tool returns RATE_LIMIT with a retry-after hint.
  3. The orchestrator's step-retry layer sees the retryable category, waits with exponential backoff plus jitter, and retries.
  4. The second attempt succeeds. The breaker records the success, the request completes.

If the rate-limit persisted across all retries, the request would fail with a clean structured error rather than a hang. If many agents were hitting the same rate-limited tool, the breaker would eventually open and shed load. If a code path inside the tool panicked instead, the panic would be caught and converted into a SERVICE_ERROR response. At no point does an unexpected failure crash the calling agent.

It is the right starting point for any agent that needs hardened fault isolation.

8. Async tasks and scheduling

Not every agent workflow fits inside a single synchronous HTTP request. A research-style agent that calls a dozen tools across three planning phases can take a minute or more — long enough that holding a TCP connection open is fragile and the user has no useful progress signal. A nightly batch that runs at 2 AM is not even waiting for a user request. TruvaG3 ships two complementary mechanisms for these cases: async tasks for long-running synchronous-shaped work and scheduled execution for time-based work.

Async tasks — the standard HTTP-202-and-polling pattern. The client sends a request, the API returns immediately with a task ID and 202 Accepted, and the work continues in the background. The client then polls a status endpoint until the task is complete. The bundled agent-with-async example wires the framework's orchestration.NewTaskAPIHandler at /api/v1/tasks:

  1. POST /api/v1/tasks with the request body → returns {"task_id": "...", "status": "queued", "status_url": "/api/v1/tasks/<id>"}.
  2. GET /api/v1/tasks/<id> → returns {"status": "running", ...} while work is in flight.
  3. GET /api/v1/tasks/<id> after completion → returns the full response payload.

Step-completion callbacks during execution write progress updates into the task store, so the polling client gets meaningful state. The duration of each task and the wait time before it is picked up by a worker are both instrumented (canonical OTEL names): executor.task.duration_ms, executor.task.wait_ms, executor.tasks.submitted, executor.tasks.completed. A wait-time histogram that starts climbing is the canonical signal that you need more workers.

Scheduled execution — three primitives that cover everything. A scheduler-tool capability lets any agent or external system create a schedule against any target agent. The three primitives are mutually exclusive (exactly one per schedule):

  • delay — relative one-shot. Go-duration string like "30s", "10m", "2h". Useful for follow-ups: "check this order status in 15 minutes".
  • run_at — absolute time. RFC3339 timestamp like "2026-06-01T18:00:00Z". Useful for one-off events: "send a reminder at 6 PM on launch day".
  • cron_expr — recurring. Standard five-field cron syntax (*/5 * * * *, 0 9 * * 1-5, etc.) parsed by the well-established robfig/cron/v3 library. Useful for periodic work: "run the daily compliance check every morning at 9 AM."

The architecture has three roles, each independently deployable:

  1. Scheduler-tool — the create/update/delete API for schedules. It is just another TruvaG3 tool, discoverable like everything else.
  2. Scheduled-executor — a worker that polls the schedule store for due work, atomically claims it (so two workers cannot fire the same schedule twice), and dispatches the task to the target agent. Scales horizontally — add replicas to handle more schedules.
  3. Target agent — any agent that registers a scheduled handler. One-line wiring opts in; the agent then receives scheduled requests through the same orchestration pipeline that handles synchronous chat requests.

Two delivery models for different reliability needs. Both async tasks and scheduled execution sit on a pluggable backend interface, with two bundled implementations:

  • At-most-once (default, Redis lists) — once a worker pops a task off the queue, it is gone from the queue. If the worker crashes mid-execution, the task is lost. Cheap, simple, fine for idempotent work and best-effort schedules.
  • At-least-once (Redis Streams) — uses consumer groups with explicit acknowledgement. A claimed task that is not acknowledged within a timeout is redelivered to another consumer. The worker may see the same task twice if it crashes — design your handler to be idempotent. Right choice for financial actions, compliance jobs, or anything where missing a scheduled run is worse than running it twice.
  • In-memory — for tests and local development. Same interface, no Redis dependency.

Switching between modes is a wiring change in the agent's main.go — no application logic moves. The right choice depends on what failure mode is more expensive in the workload, not on what the framework forces.

Live metrics across both flows.

  • Async tasks: async_orchestration.tasks (labeled by status: completed, failed, setup_failed, catalog_failed), async_orchestration.duration_ms, async_orchestration.tool_calls, async_orchestration.tools_per_query. The last one is particularly useful: it tells you the typical "fan-out" of an async request, which feeds capacity planning.
  • Scheduled execution: executor.tasks.submitted vs executor.tasks.completed shows backlog at a glance. executor.task.wait_ms shows queue latency; executor.task.duration_ms shows execution latency. A widening gap between submitted and completed is the canonical "add workers" signal.

Working examples in the cluster. The agent-with-async example demonstrates the full async pattern — API mode, worker mode, and embedded mode (API + worker in one process for simple deployments). The scheduler-tool and scheduled-executor examples make up the complete scheduled-execution stack — the tool runs as a regular framework tool, the executor runs as an independently scalable worker pool, and any target agent can subscribe in one line.

9. Human-in-the-loop

Some decisions are too consequential for an agent to make alone — placing a financial trade, deleting production data, sending mass communications, approving a refund above a threshold, executing infrastructure changes against a live cluster. Regulated industries also require human approval points as a compliance control. TruvaG3 ships a complete Human-in-the-loop (HITL) system that pauses an in-flight request at well-defined moments, persists the execution state, notifies a reviewer, and resumes — or aborts — based on the reviewer's decision. The agent's request path stays continuous from the user's perspective even when a human takes minutes or hours to respond.

Five interrupt points cover every decision moment. The orchestrator can pause at any of these — chosen by policy, not hard-coded:

  • plan_generated — pause right after the LLM produces a plan, before any step runs. The reviewer sees the entire DAG and can approve, edit, or reject. Useful for high-stakes workflows where the whole shape of the action matters.
  • before_step — pause before a specific step executes. Useful for fine-grained control: approve every individual write to a sensitive system while letting reads pass freely.
  • after_step — pause after a step completes but before the orchestrator continues to the next phase. The reviewer sees the actual result, not just the intent, and can decide whether to proceed. Useful when the next decision depends on what the previous step actually returned.
  • on_error — escalate to a human when a step fails in a way the framework's automatic recovery cannot handle. Default action is to abort the workflow, since errors that reach this point are usually genuinely unrecoverable.
  • context_gathering — pause to ask the reviewer for information the agent cannot obtain on its own (a missing identifier, a free-text justification, a policy override).

Seven decision types — not just "yes" or "no". When a checkpoint fires, the reviewer responds with one of:

  • approve — proceed as planned.
  • edit — proceed with modifications. The reviewer can rewrite the plan, change step parameters, or tweak the response before it goes out. The orchestrator picks up the modified version and continues.
  • reject — reject the proposed action. The workflow stops cleanly with a structured rejection response.
  • skip — skip the current step and continue with the rest of the plan. Useful when one step is irrelevant but the rest of the workflow should still run.
  • abort — stop the entire workflow immediately, no continuation.
  • retry — retry the step with new parameters supplied by the reviewer. Useful for fixing a known issue the LLM did not anticipate.
  • respond — supply the information the agent requested (for context_gathering interrupts).

This richness matters in practice. An approval workflow that only offers "approve" and "reject" forces a back-and-forth (reviewer rejects, agent regenerates, reviewer reviews again). With edit and retry, a reviewer can make a single-touch correction and let the workflow continue — turning a five-minute round-trip into a one-second adjustment.

Persistent checkpoints with atomic claim. When an interrupt fires, the orchestrator saves a full ExecutionCheckpoint to a Redis-backed store: the current plan, all completed step results, the LLM context, the conversation history, and the interrupt reason. A reviewer's decision arrives — possibly minutes or hours later — through any channel: REST API, webhook callback, or SSE stream from a chat UI. The framework atomically claims the checkpoint before processing the command, so even if the same approval is submitted from two browser tabs by accident, only one command runs (orchestration.hitl.claim_success_total and orchestration.hitl.claim_skipped_total track claim outcomes).

Auto-resume on timeout, fail-safe by default. Every checkpoint has an expiration TTL. When the TTL elapses without a decision, the framework runs a configurable DefaultAction:

  • The default DefaultAction is reject — fail-safe, the high-stakes action does not happen automatically.
  • For on_error escalation, the default is abort — workflow stops cleanly.
  • Both are overridable per deployment via TRUVAG3_HITL_DEFAULT_ACTION or per checkpoint via policy.

The expiry processor scans expired checkpoints in batches; orchestration.hitl.expiry_batch_size and orchestration.hitl.expiry_scan_duration_seconds tell you whether the processor is keeping up.

Webhook notification, pre-built. Reviewer notification is not the framework's problem — it ships a WebhookInterruptHandler that fires an HTTP POST to a configured URL the moment a checkpoint is created. From there, the integration layer (Slack, Teams, PagerDuty, an internal approval system, a custom dashboard) takes over. orchestration.hitl.webhook_sent_total tracks webhook delivery counts; orchestration.hitl.webhook_duration_seconds tracks the round-trip latency to the notification endpoint.

Approval-latency metric — measure your human SLA. orchestration.hitl.approval_latency_seconds is the time from checkpoint creation to decision. This is the canonical "how fast does my human approver respond" metric, and it directly drives user-facing latency for HITL-gated workflows. A team running a 95th-percentile dashboard on this metric can prove (or disprove) compliance SLAs at any moment.

Working example in the cluster. The agent-with-human-approval example demonstrates the complete pattern: SSE for real-time browser notification, a structured approval dialog, plan-level and step-level approval chained together, auto-resume on timeout, and edit support so the reviewer can rewrite a plan in one round-trip. It is the right starting point for any agent that needs human gating.

10. Memory and context

A stateless agent starts every request from zero — it does not remember the user's last question, the answer it gave five minutes ago, the long-running investigation that other agents in the same domain have been working on, or the user's stated preferences. For some workflows that is fine. For chat agents, multi-step research, ongoing investigations, and assistant-style products it is not — context across requests is the difference between a helpful agent and an amnesiac one. TruvaG3 ships a three-tier memory system that covers everything from small per-component state to vector-backed semantic recall, with separate stores for shared agent memory and per-user memory so a single agent process can serve many users without leaking one user's facts to another.

Layer 1: Component key-value memory. A simple per-component core.Memory interface with Get, Set, Delete, and Exists. Useful for small local state — a session counter, a cached API response, a transient flag — that does not need to be shared across replicas. Two implementations ship: in-memory for tests and Redis-backed for production. Every operation is counted under memory.operations (labeled by op), with eviction activity under memory.evictions.

Layer 2: Shared agent memory. A richer store designed for agents that work in a shared domain — a fleet of DevOps agents investigating the same incident, a team of research agents covering related topics, a set of compliance agents tracking related policy changes. Three substores:

  • Episodic events — append-only log of meaningful events: tool calls made, findings discovered, decisions taken. Backed by Redis in production, in-memory for tests.
  • Knowledge store (vector-backed) — semantic search over learned facts and prior conclusions, with Qdrant as the reference vector backend. Fragments are stored (memory.knowledge.fragments_stored), searched (memory.knowledge.search.success / memory.knowledge.search.errors), and surface as relevant context in the prompt when a request comes in. The cache layer is instrumented separately: memory.cache.hits / memory.cache.misses tell you whether vector queries are hitting cache.
  • Activity coordination — lightweight signals between concurrent agents so they do not duplicate work. Agent A announces "I am investigating order #1234," and Agent B sees the announcement and skips that work. Backed by Redis distributed locks with a TTL.

Reflection — periodic LLM-driven memory consolidation. Raw episodic events accumulate quickly. Left alone, they would make the knowledge store either too noisy (every event surfaces) or too sparse (only recent events surface). The framework ships an opt-in ReflectionJob that periodically reads episodic events older than a configurable threshold (default 7 days), summarizes them through the LLM into stable knowledge fragments, and stores the result in the vector-backed knowledge store. Each pass is wrapped in a memory.reflection_pass span; counters memory.compaction.runs_total and memory.compaction.fragments_created, plus the histogram memory.compaction.duration_ms, expose throughput and failures (memory.compaction.reflection_errors). The effect is similar to what a human team does in a retrospective — extract the durable lessons from the ephemeral activity, and move on.

Layer 3: Per-user memory. For assistant-style agents that serve many users, the framework keeps a separate per-user memory store with three distinct stages, each instrumented:

  • Extraction — at the end of a conversation, an LLM call extracts candidate facts from what the user said (user_memory.extraction and user_memory.extraction.llm spans in the trace; user_memory.remember.duration_ms histogram).
  • Reconciliation — each candidate fact is checked against existing facts about that user. The LLM classifies the relationship as one of four operations: ADD (new fact), UPDATE (refines an existing fact), CONTRADICT (replaces a now-wrong fact), or DUPLICATE (already known, discard). Tracked by user_memory.reconciliation.operation labeled by operation type. The contradict path is the most important one in practice — it lets the agent gracefully update its model of the user when they say "actually, never mind, I prefer X now."
  • Recall — when a new request arrives, the framework runs five distinct recall paths in parallel and merges the results: identity (facts about who the user is), stable_namespace (facts tagged with stable identifiers), query (semantic match against the current request), summary (rolling user summary), and universal (facts that always apply). Each path is its own span — user_memory.recall.{path} in Jaeger — so you can see which paths contributed to a given response. Total recall latency is user_memory.recall.duration_ms.

Per-user memory supports GDPR-style "forget" — a single API call removes every fact, embedding, and summary tied to a user ID. Important for any deployment that has users in regions with right-to-erasure laws.

Conversation history protection — three tiers, automatic by default. Chat agents accumulate messages across turns; left unmanaged, the conversation buffer eventually overflows the LLM's context window. TruvaG3 handles this transparently:

  • Tier 1 (default) — token-budgeted enrichment. Raw turns flow through, with the framework tracking token estimates (conversation_history.estimated_tokens) and emitting conversation_history.prepare spans on every request.
  • Tier 2 (opt-in) — recursive compaction. When a session grows past a configurable threshold, older turns are summarized into a rolling "earlier in this conversation..." block by the LLM, freeing budget for the live exchange. Compaction events are counted (conversation_history.compactions.total) and their duration tracked (conversation_history.compaction.duration_ms). A summary cache (conversation_history.summary_cache.size) prevents re-summarizing the same older turns on every request.
  • Tier 3 (custom) — for teams with specific compaction rules (preserve every tool result, drop greetings, structure by topic), the ConversationCompactor interface lets you supply your own logic while reusing the rest of the pipeline.

Most teams never touch Tier 2 or 3 — Tier 1 with the default budget handles typical chat workloads. The system is layered so the work shows up only when the workload requires it.

Pipeline hooks are how memory connects to the request path. All three memory layers are wired into the orchestrator through pipeline hooks (see §13 for the four hook stages). Memory recall typically runs in a BeforePlanningHook (so recalled facts and conversation history enter the planning prompt); memory extraction typically runs in an AfterSynthesisHook (so facts learned during the request are persisted). This means memory is configurable per agent — a tool-only deployment can opt out entirely, a chat agent enables all three layers, and a regulated workflow can swap in a custom hook that audits every memory write.

Working examples in the cluster. The travel-chat-agent and devops-chat-agent both wire shared memory and per-user memory through pipeline hooks (see UserMemoryBackend / BuildUserMemoryHooks in their chat_agent.go). Their Jaeger traces show the full memory flow — recall paths firing on the request path, extraction firing after synthesis — exactly as described above.

11. Chat agent reference pattern

Building a practical chat agent involves more than calling an LLM. The agent needs to stream responses (long answers must not block on a final newline), maintain session state (the user expects you to remember the previous turn), support multi-turn context without overflowing the context window, integrate with human-in-the-loop approval flows for sensitive actions, and survive page refreshes, network blips, and concurrent tabs. TruvaG3 ships a complete reference pattern that handles all of this. The pattern is exercised by the bundled chat agents (travel-chat-agent, devops-chat-agent) and consumed by the bundled chat-ui frontend.

Server-Sent Events stream eight distinct event types. Rather than streaming opaque token chunks, the chat pattern emits a typed event stream so the frontend always knows what kind of update it just received:

  • session — new session created. Carries the session ID the client should attach to subsequent requests.
  • status — progress update (e.g., "Phase 2 of 3...", "Analyzing weather data..."). The frontend renders this as a spinner-with-context, not a blank loading state.
  • step — a tool call completed. Carries the tool name, success flag, and duration. Power-user dashboards render the per-step execution; consumer UIs filter these out.
  • chunk — a part of the AI's response text. Streamed token-by-token so the user sees the answer appearing as it generates.
  • usage — token stats for the request (prompt, completion, total). Useful for showing cost transparency in admin UIs.
  • finish — the stream is ending and here is why (stop, length, tool_calls, etc.).
  • done — the request is complete. Carries the request ID and total duration so the frontend can show the final timing.
  • error — something went wrong. Carries a structured error code, a human-readable message, and a retryable flag so the frontend can decide whether to surface a retry button.

This typed event surface is the difference between a chat UI that feels rough at the edges and one that feels polished. A frontend developer can wire each event type to a specific UI affordance without parsing message text or guessing at intent.

Session storage with sliding-window history. Sessions are stored in Redis with a configurable TTL and a maximum-messages limit (when the message count exceeds the cap, the oldest messages are evicted automatically — a sliding window over the conversation). The session record carries the user ID, metadata, message history, and timing fields. Three Redis structures back this: the session record itself, a per-user index of that user's active sessions, and an active-session counter for capacity dashboards. A background cleanup process removes expired sessions on a schedule so the Redis footprint stays bounded.

Multi-turn context flows automatically into orchestration. A chat request body carries the session ID; the framework looks up that session's recent messages, packages them into orchestration metadata, and the conversation-history layer (see §10) handles the rest — Tier 1 enrichment by default, Tier 2 compaction for long sessions. The agent's request handler does not have to do anything special; multi-turn just works.

HITL resume that preserves the conversation. When a chat request hits a human-in-the-loop checkpoint (see §9), the framework persists the session context alongside the checkpoint. Hours later, when the reviewer approves, the resume endpoint (POST /hitl/resume/{checkpoint_id}) restarts execution inside the same chat session — the orchestrator picks up where it left off, the conversation history is intact, and the SSE stream continues delivering events to whichever client is currently watching. The user sees a seamless conversation; the operator sees a clean audit trail of who approved what.

Frontend reference, ready to clone. The bundled chat-ui example ships several HTML frontends that consume the SSE event stream: a generic chat interface, a DevOps-styled chat (for the devops-chat-agent), a HITL approval dashboard, and a dashboard overview. They are deliberately plain HTML + vanilla JavaScript so they are easy to read and adapt — no framework lock-in, no build step. Any production chat product would replace them with a real frontend, but they are a complete starting point that exercises every event type and shows what good handling looks like.

Working examples in the cluster. travel-chat-agent and devops-chat-agent wire the full pattern end-to-end. Both expose /chat/stream (SSE) plus the session-management capabilities (/chat/session, /chat/session/{id}, /chat/sessions, etc.), use Redis-backed session stores, and integrate with HITL where applicable. devops-chat-agent specifically demonstrates the HITL-resume-in-chat flow, since most DevOps actions need human approval before touching production. The companion qa-agent is a non-streaming orchestration agent (POST /query) that drives autonomous test exploration — it shares the orchestration stack but does not use the SSE chat pattern.

12. Security and request propagation

The framework takes a deliberately small position on security: it does not replace your identity provider, your service mesh, your ingress controller, your network policies, or your secrets manager. Those tools exist, your platform team operates them, and they work on TruvaG3 components the same way they work on every other REST service in the cluster — because TruvaG3 components are REST services. What the framework adds on top of that is the small set of hooks and propagation points that an agent workload specifically needs: passing user tokens through a chain of agent and tool calls, attaching tenant and audit metadata that flows the same way, and protecting a handful of framework-internal headers from being accidentally overwritten.

Three ways to attach an OAuth Bearer token to outbound calls. The orchestrator can attach an Authorization: Bearer ... header to every tool and agent call it dispatches, with three resolution paths to suit different deployment shapes:

  • Environment variable — the simplest path. Set TRUVAG3_OAUTH_TOKEN at deploy time; every outbound call gets the token attached. Right for static service-to-service tokens.
  • Config object — pass the token (or a token source) into the orchestrator at construction. Right when the token is loaded from a vault or a secret manager at startup.
  • Per-request context injection — the most flexible path. The agent's HTTP handler extracts the user's token from the incoming request and passes it through Go's context.Context; the orchestrator uses that token for every downstream call this request makes. Right for user-token pass-through, where each request runs as the calling user.

The three paths layer cleanly: per-request context overrides config, config overrides environment. Most deployments use a combination — for example, a default service token from env, with per-request user tokens overriding when present.

Runtime token refresh, no restart needed. Service tokens expire. When yours does, you call SetOAuthToken(newToken) on the orchestrator and every subsequent outbound call uses the new token. The implementation uses atomic.Value internally, so the refresh is thread-safe — in-flight requests already using the old token complete normally, and new requests get the new token, with no synchronization gap. Token refresh is a runtime operation, not a deploy.

Custom header propagation for tenant, audit, and correlation metadata. Agent workloads almost always need to carry context beyond the auth token — a tenant ID for multi-tenant routing, an audit correlation ID for compliance trails, a feature-flag bucket for A/B testing. The framework supports two layers:

  • Config-level defaults — set PropagatedHeaders on the orchestrator config (e.g., {"X-Tenant-ID": "acme", "X-Environment": "prod"}) and every outbound call carries them. Useful for deployment-wide context.
  • Per-request overrides — set headers on the request context via WithPropagatedHeaders(ctx, ...) and they override config-level defaults for that one request. Useful when each request has its own tenant or correlation context.
  • Header field name protection — the JSON serialization of the config struct explicitly excludes PropagatedHeaders (the field is tagged json:"-") so headers never leak into request logs or telemetry by accident.

Nine framework-internal headers are protected from overwriting. The orchestrator sets two standard HTTP headers and seven X-TruvaG3-* headers on every outbound call. These are reserved — even if a developer sets the same key in PropagatedHeaders, the framework's value wins. This prevents subtle breakage of authentication, trace correlation, or HITL resume:

  • Authorization and Content-Type — reserved so a stray propagation cannot override the bearer token or the body format.
  • X-TruvaG3-Request-ID — the orchestrator-assigned ID for this top-level request. Used for log and trace correlation end-to-end.
  • X-TruvaG3-Step-ID — the specific step within the plan this call corresponds to. Tied to the per-step span in the trace.
  • X-TruvaG3-Agent-Name — which agent originated the call. Useful for downstream RBAC checks.
  • X-TruvaG3-Phase-Number — for multi-phase iterative plans, which phase this call belongs to.
  • X-TruvaG3-Plan-ID — the plan this call is part of.
  • X-TruvaG3-Original-Request-ID — for chained agent-to-agent calls, the request ID at the very top of the chain. Lets one trace cover the full fan-out.
  • X-TruvaG3-Investigation-Owner — for shared-memory activity coordination, identifies which agent currently owns an ongoing investigation.

Any of these headers arriving at a tool can be used for fine-grained authorization, audit logging, or correlation — none of them are framework-internal in the sense of being hidden.

Secrets and configuration follow Kubernetes conventions. API keys, OAuth tokens, and provider credentials are read from environment variables, sourced from Kubernetes Secrets. Non-sensitive configuration (registry URL, log level, feature toggles) is sourced from ConfigMaps. The framework imposes no special key-management system — whatever secrets workflow your platform team uses (ExternalSecrets, Sealed Secrets, Vault sidecars, plain Secrets) works without adaptation.

Developer-tool exposure is off by default. OpenAPI generation is disabled until you explicitly enable it, because the /openapi.json document describes the component's full API surface and most internal services do not need to expose that publicly. The Registry Viewer and Swagger UI are developer tooling, not production endpoints — they should be protected at the network, gateway, or mesh layer just like a database admin console or a Prometheus query UI.

What this looks like end-to-end. A user request hits the agent's ingress with an Authorization header. The agent extracts the user's token, passes it through context, and calls a downstream tool. The orchestrator's outbound call carries: the user's Authorization token (per-request, from context), the tenant ID (config-level), the framework's request ID and step ID (protected). The tool authenticates the user via your existing identity provider, logs the request ID for audit, applies tenant-scoped authorization, and returns. Trace, logs, and audit data all correlate by the request ID. Nothing about this flow is framework-specific — it is the same pattern a well-built REST microservice deployment already uses.

13. Extension points

The framework exposes interfaces at the boundaries where teams are most likely to need replacement. Each is behind a Go interface with a default implementation. The main extension points, with examples from the bundled agents:

Pipeline hooks. Per-stage middleware around the orchestration pipeline. Hooks let application code inject context, short-circuit processing, mutate plans, or post-process responses — without forking the framework. There are four stages:

  • BeforePlanningHook — runs before the planner. Inject RAG context, conversation history, or a semantic-cache lookup. The only stage that can short-circuit the entire pipeline (return a cached response without calling the LLM at all).
  • AfterPlanningHook — runs after the LLM produces a plan. Mutate or validate the plan before execution.
  • AfterExecutionHook — runs after all tool calls finish. Observe-only — used for analytics, audit logging, and metrics.
  • AfterSynthesisHook — runs after the final response is generated. Apply PII redaction, content policy checks, or write the response into memory.

Hooks are resilient by design — a failing hook logs a warning and the pipeline continues. The travel-chat-agent and devops-chat-agent examples wire memory hooks across these stages to give chat agents conversation history, semantic recall, and audit trails.

Custom prompt builders. Replace the prompt-construction logic while preserving orchestration interfaces. Useful for compliance instructions, custom output formats, or tenant-aware system messages. The agent-with-orchestration example configures a custom prompt builder with travel-specific type rules so the planner understands domain types out of the box.

Pluggable backend interfaces. Every backend the framework relies on sits behind a Go interface. Defaults work out of the box; alternatives can be wired in without changing application code:

  • core.Discovery — service registry (default: Redis or Valkey; in-memory mock ships for tests; other backends such as etcd or Consul require a user-written adapter against the same interface).
  • core.AIClient — LLM provider client (default: auto-detected provider registry; chain-client failover and custom providers also supported).
  • core.Memory — per-component key-value memory (Redis in production, in-memory for tests).
  • core.TaskQueue and core.TaskStore — async task backends (Redis lists by default; Redis Streams also bundled). The agent-with-async example wires the full request → task-ID → poll pattern on the default Redis backend.
  • core.ScheduleStore, core.TaskDispatcher, core.TaskConsumer — scheduled-execution backends, used by the scheduled-executor example.
  • Embedding client, LLM debug store, execution debug store — all behind interfaces with default implementations.

The framework also ships in-memory implementations of every interface plus a core/conformance package that validates custom backends against the same contract the defaults meet.

Custom result processors. The ResultProcessor interface controls how large tool and agent results are trimmed before they enter LLM prompts. The default StructuralTrimmer preserves JSON structure, key names, and representative samples within byte budgets. Teams with domain-specific outputs (large clinical datasets, deeply nested telemetry payloads) can replace it behind the same interface.

What it looks like in code

Three short examples to make the framework concrete. They are simplified versions of the bundled examples.

A tool

A tool exposes one or more capabilities over HTTP. Here is a weather tool that registers a single capability:

tool := core.NewTool("weather-service")
tool.RegisterCapability(core.Capability{
    Name:        "current_weather",
    Description: "Gets current weather conditions for a location.",
    Handler:     handleCurrentWeather,
})

framework, _ := core.NewFramework(tool,
    core.WithName("weather-service"),
    core.WithPort(8080),
    core.WithRedisURL(os.Getenv("REDIS_URL")),
    core.WithDiscovery(true, "redis"),
)
framework.Run(ctx)

That is the whole tool. The framework registers current_weather into the registry, exposes it at /api/capabilities/current_weather, refreshes the heartbeat every 15 seconds, and shuts down gracefully on a signal.

An agent that uses tools it has never heard of

An agent does not need to know which tools exist. It hands the user request to the orchestrator, which reads the live registry and produces a plan:

orchestrator := orchestration.CreateOrchestrator(config, deps)

response, _ := orchestrator.ProcessRequest(ctx,
    "What is the weather in Tokyo and the stock price of Apple?", nil)

The orchestrator discovers whatever capabilities are currently registered, asks the LLM for a plan, executes the plan as a DAG, and synthesizes the response. The agent's source code names no tool. Deploy a new tool five minutes later, and the same agent can use it on the next request — no code change, no redeploy.

The bundled examples show the same agent picking different capabilities depending on the question. "Weather in Paris" routes to get_current_weather (served by weather-tool-v2); "stock price of Apple" routes to stock_quote (stock-market-tool); "Capital of Japan" routes to get_country_info (country-info-tool). No hardcoded routing — the LLM picks the capability from the live registry and the framework resolves it to the address.

One agent calling another

From the calling agent's point of view, an agent and a tool look the same. Both register capabilities into the same registry. Both are dispatched through the same HTTP call. The architecture article walks through a captured multi-domain trace where travel-chat-agent handles a user request that crosses three domains. Its four-step plan includes devops_operations, geocode_location, stock_quote, and get_current_weather. One of those — devops_operations — happens to be served by another agent (devops-chat-agent), which runs its own internal plan-execute-synthesize loop. From the dispatch site, there is no visible difference between the agent step and the tool steps.

Run it on a laptop

The full TruvaG3 stack — registry, the bundled tools and agents, the Registry Viewer, and an OpenTelemetry pipeline — runs on a laptop in a local Kubernetes cluster (Kind). The setup guide walks through the cluster, the Redis or Valkey backend, the AI provider configuration, and the bundled examples.

The two captured executions in the architecture article — the three-phase Switzerland trip plan and the multi-domain agent-to-agent run — both come from this setup. Once the bundled examples are deployed, the same user queries can be run against the same agents, and the Registry Viewer's Execution DAG tab will produce equivalent screenshots and trace JSON files. Nothing in either article is theoretical.
